## What it is

The `push-notifications` module is push over Firebase Cloud Messaging (FCM), using [`@react-native-firebase/app`](https://rnfirebase.io) and `@react-native-firebase/messaging` 27. On iOS the messages travel through APNs, which FCM talks to for you.

It is **off by default**, **needs the [`firebase-core`](/docs/features/firebase-core) module** (added automatically) and **your own Firebase projects**, ideally one per environment. The Firebase config files are not in the template, and the app builds and runs without them: push is simply off.

What you get, all in `src/services/push`:

- A token handler, `setPushTokenHandler(fn)`, where your app sends the FCM token to its backend.
- A permission request, `requestPushPermission()` and the `usePushPermission()` hook, used by a **Notifications** row in Settings. Nothing is asked at startup.
- Foreground messages shown as an in-app toast.
- Notifications that arrive in the background or while the app is closed are shown by the operating system. Pressing one opens the screen named in `data.link`.
- A background message handler registered in `index.js`.

## Limits

This module is deliberately small. Know these before you choose it:

- **No local or scheduled notifications.** Only messages sent by your server through FCM.
- **No rich foreground notification UI.** A message that arrives while the app is open is a toast with a title, a body and an optional press action. It is not a system notification, and there are no custom actions, images or sounds.
- **One Android channel**, `default`. The operating system displays background notifications from the `notification` part of the FCM payload; the app cannot restyle them.
- **Data-only messages are not displayed.** They reach the background handler and nothing else. Your app decides what to do with them.

Teams that need local notifications, scheduling, channels per topic or custom layouts add a notification library on top. The community fork [`react-native-notify-kit`](https://github.com/marcocrupi/react-native-notify-kit) of Notifee is one option (Notifee itself is archived and no longer maintained). That is a recipe, not part of this module.

## Enable and remove

<CommandTabs yarn="tempo feature add push-notifications" npm="npx tempo feature add push-notifications" />

<CommandTabs yarn="tempo feature remove push-notifications" npm="npx tempo feature remove push-notifications" />

Removal deletes `src/services/push`, the bootstrap step, the Settings row, the translations, the Android channel code and strings, the `PUSH_ENABLED` lines and the messaging dependency, then runs `pod install`. `firebase-core` stays, because other modules may use it.

## Native requirements

React Native Firebase 27 sets some floors that reach the whole app:

- **iOS: dynamic frameworks.** Firebase 13 comes only through Swift Package Manager, which needs `use_frameworks! :linkage => :dynamic`. The module adds `linkage ||= 'dynamic'` to the Podfile, so **every** pod is built as a dynamic framework while the module is present. Static linkage is rejected by `pod install`. If a pod of yours cannot be linked dynamically, remove the module or stay on RNFB 26, which still has a CocoaPods path.
- **Android: `minSdk` 24** (already the template's value). RNFB 27 asks for Kotlin 2.4 or newer for some packages (Firebase Auth); the app builds with the template's Kotlin 2.2 because it uses only `app` and `messaging`. If you add Auth or other Firebase modules, raise `kotlinVersion` in `android/build.gradle`.
- **New Architecture only.** Already on in this template.

## Push per environment

Push is switched **per environment in `.env.<env>`**, nothing else:

| Key | Meaning |
| --- | --- |
| `FIREBASE_ENABLED` | The environment uses Firebase: its config files are copied into the build ([Firebase per environment](/docs/features/firebase-core)). |
| `PUSH_ENABLED` | The environment uses push. Needs `FIREBASE_ENABLED=true`. |

Push is on only when **both** are `true` and the native Firebase app exists. When it is off, `initPush` and the permission calls do nothing (no listeners, no token, no prompt) and the **Notifications** row in Settings is hidden. `firebase.json` also keeps FCM auto-initialisation off (`messaging_auto_init_enabled: false`), so an environment with push off never registers with FCM; `initPush` turns it on with `setAutoInitEnabled` only when push is on.

| Environment | `FIREBASE_ENABLED` | `PUSH_ENABLED` | Result |
| --- | --- | --- | --- |
| dev (default) | `false` | `false` | No Firebase, no push, no row. |
| dev with its own project | `true` | `true` | Push against the dev project; files in `firebase/dev/`. |
| staging | `true` | `true` | Push against the staging project. |
| prod | `true` | `true` | Push against the production project. |
| prod, push not shipped yet | `true` | `false` | Firebase on (for crash reporting), push off. |

Defaults of the template: dev off, staging and prod on, `PUSH_ENABLED=false` in the committed `.env.dev` and `.env.example`. Set `true` in your `.env.staging` and `.env.prod`.

## Set up Firebase

1. Create one Firebase project per environment and add the Android and iOS apps of that environment. Follow [Firebase per environment](/docs/features/firebase-core#set-it-up); it covers the project, the app ids, where to save the files, `FIREBASE_ENABLED` and CI.
2. Set `PUSH_ENABLED=true` in the env files of the environments that use push.
3. Upload the APNs key to **each** Firebase project (next section).

### APNs key and iOS capabilities

Push on iOS needs an Apple developer account. One APNs key works for every project of your team, but it must be uploaded to **every Firebase project** that sends to iOS: each environment's iOS app lives in its own project.

1. In the Apple developer portal create an **APNs authentication key** (`.p8`), and note the key ID and your team ID.
2. In the Firebase console of **each environment's project**, open **Project settings, Cloud Messaging**, and upload the key for that project's iOS app (development and production).
3. In Xcode, add the **Push Notifications** capability to the target. This adds `aps-environment` to `ios/TempoApp/TempoApp.entitlements`.

The template's entitlements file does **not** contain `aps-environment`: an unsigned simulator build fails when the entitlement is present, and the file has no team to sign with. Add it together with the capability once you have a team. `UIBackgroundModes` with `remote-notification` is already in `Info.plist`.

The module registers for remote notifications through React Native Firebase's method swizzling, which is on by default.

<Callout type="warn" title="Simulators">
  The iOS simulator on Apple silicon does not receive APNs messages, and React Native Firebase skips the registration there. Test push on a physical iPhone. Android emulators with Google Play services work.
</Callout>

## Send a test message

1. Run a build of an environment with `PUSH_ENABLED=true` on a device with the config files in place. Allow notifications in Settings, Notifications.
2. Get the token: set a handler in your own code, for example in a bootstrap step or after sign-in:

   ```ts
   import { setPushTokenHandler } from '@services/push/push';

   setPushTokenHandler(async (token) => {
     await request({ url: '/devices', method: 'POST', data: { token } }, DeviceSchema);
   });
   ```

   The default handler only logs "token received" and never the token itself. While developing, you can temporarily `console.log` it in your own handler; do not commit that.

3. In the Firebase console open **Messaging, Create your first campaign, Firebase Notification messages**, send a test message to the token. Add the custom data `link` = `items/5` to test routing.

Close the app to test the system-displayed notification and the cold-start press, put it in the background to test the warm press, and keep it open to see the toast.

## Payload contract

Send the display text in the FCM `notification` part and extra data in `data`. The app reads one data key:

```json
{
  "message": {
    "token": "<device token>",
    "notification": { "title": "Order shipped", "body": "Your order #5 is on its way" },
    "data": { "link": "items/5" }
  }
}
```

`data.link` is **a path of this app**, the same paths as deep links (`items/5`, `settings/theme`; see `LINK_PATHS` in `src/navigation/linking.ts`):

- It must be relative: letters, digits, `-`, `_` and `/`. No scheme, no host, no query, no `..`. A full `https://...` or other-app link is ignored.
- It must match one of the app's own paths. An unknown path is ignored.
- Ignored links log one `warn` line that names no part of the payload.

A valid link is opened through the normal deep link pipeline as `<scheme>://<path>`. So everything deep links already do applies: a **signed-out user is taken to Login and the link is replayed after sign-in** (`pendingLink`). A notification that starts the app is opened after startup finishes and the navigator exists. If several arrive before that, the last one wins.

A foreground message shows a toast with the `notification` title and body. When it has a valid `data.link`, pressing the toast opens it.

## Permission UX

The module never asks at startup. The first request belongs at a moment the user understands, after they asked for it or after a screen explains why.

- The Settings **Notifications** row is the built-in place: turning it on asks, with the system prompt. If the system will not ask again (after a refusal), the row says so and opens the system settings; turning it off also opens the settings, because an app cannot revoke its own permission.
- Anywhere else, call `requestPushPermission()`. It resolves to `'granted'`, `'denied'` (the user said no just now, you may ask again later) or `'blocked'` (the system will not show the prompt; send the user to the settings with `openSettings()` from `@services/linking/linking`). It never throws.
- `usePushPermission()` returns `{ status, request }`, refreshes when the app returns to the foreground, and reports `'undetermined'` before the first answer.
- iOS asks once per install. Android 13 and later asks through `POST_NOTIFICATIONS`; before Android 13 notifications need no permission. Android does not say whether it has ever asked, so a not-yet-granted state reads as `'undetermined'`, and the `'blocked'` answer arrives when you request.
- After a grant the token is fetched again and handed to your token handler.

## Privacy

- **No payload is ever logged.** Title, body, data values and tokens never reach the logger. The logs hold event kinds ("notification pressed", "message received in the foreground") and message ids at `debug`. A test fails if that changes.
- The foreground toast shows the title and body on screen and nowhere else.
- Treat the token as a device identifier: send it only to your own backend, over HTTPS, tied to the signed-in user, and delete it on sign-out.
- Tokens and `data` are not encrypted by FCM end to end. Do not put personal data in `data`; put an id and load the details after the screen opens.

## How it works

| Part | File |
| --- | --- |
| Token, foreground toast, press handling | `src/services/push/push.ts` |
| Permission and hook | `src/services/push/permission.ts` |
| `data.link` parsing and opening | `src/services/push/routing.ts` |
| Background handler (registered in `index.js`) | `src/services/push/background.ts` |
| The only file that calls RNFB token and permission APIs | `src/services/push/fcm.ts` |
| Whether push is on (`isPushEnabled`) | `src/services/push/firebase.ts` |
| Bootstrap step, after auth, never fatal | `src/app/bootstrap/initPush.ts` |
| Settings row | `src/features/settings/components/NotificationsRow` |
| Android channel and strings | `MainApplication.kt`, `res/values/strings.xml`, `res/values-ar/strings.xml` |

RNFB 27 marks `getToken`, `onTokenRefresh` and `requestPermission` as deprecated in favour of Installation IDs and other libraries. They still work, `fcm.ts` isolates them, and there is one place to change when a future major removes them.

When push is off (`PUSH_ENABLED=false`, `FIREBASE_ENABLED=false` or no config file) `isPushEnabled()` is false, every call returns early with a `debug` log, and the permission request answers `'denied'` without asking.

## Customize

- **Channel name:** edit `push_channel_default` in `res/values/strings.xml` and `res/values-ar/strings.xml`. A second channel is one more `createNotificationChannel` call in `MainApplication.kt`; select it per message with `android.notification.channel_id` in the FCM payload.
- **Notification icon and colour (Android):** add `com.google.firebase.messaging.default_notification_icon` and `default_notification_color` meta-data entries to the manifest. Without an icon Android shows the launcher icon.
- **Known paths:** `isKnownLinkPath` follows `LINK_PATHS`; add a screen there and its notifications work.
