---
title: "ADR-015: Dynamic forms with a typed code config and a JSON adapter"
description: "Why dynamic forms are a typed config first, a declarative untrusted JSON format second, and Zod everywhere"
---

- **Status:** accepted · 2026-11-09

## Context
Most apps have a handful of long forms (onboarding, KYC, requests) and sometimes want the server to define one. The template already has typed, react-hook-form bound inputs (`Form*`). Three needs follow:

- Describe a form as data, with rules (show, hide, disable, compute, validate per step), a draft and a review, without a new screen per form.
- Let a server describe a form, without letting the server run code in the app.
- Keep validation one system, the same Zod schemas as the rest of the template.

The owner's FormBuilder (a typed config renderer built on react-hook-form and Yup) is the design base. ejada's `config-driven-forms` was read for ideas (serializable config, a schema built from rules, repeatable sections).

## Decision
- **A typed code config is the core.** `FormField<T>` is a discriminated union over a project `FieldTypeMap`; one registry file maps each type to an existing `Form*` component. Functions are allowed (`visibleIf`, `calculatedValue`, `asyncValidate`, `custom` render), because code is trusted and TypeScript checks it.
- **A JSON adapter sits beside it, not under it.** `fromJson` turns a validated `FormSchemaJson` or `FlowJson` document into the same typed config, plus a Zod schema built from declarative rules. Everything functional is out of the JSON format. One engine runs both, so a JSON form and its code twin behave identically (tested).
- **The JSON is untrusted.** The whole document is parsed by a strict Zod schema first: unknown keys and types are rejected, sizes are capped, names are plain identifiers, conditions are objects (`{ field, equals | notEquals | in | notIn | gt | lt | isEmpty | isNotEmpty }` with `all`, `any`, `not`), and rules are a fixed list. There is no `eval`, no `Function` and no expression string anywhere. The `pattern` rule takes a name from an allow-list in code (`digits`, `letters`, `alphanumeric`, `noSpaces`, `postalCode`, `iban`, plus the project's own), never regex source: a heuristic check for catastrophic backtracking is easy to bypass, and a linear-time engine would be a new dependency. Nothing compiles a string from the document. The code config still takes a real `RegExp`, because a developer writes it.
- **Zod 4, not Yup.** The template validates everything with Zod. The Yup schema of the original is replaced by `z.ZodType<T>` in the code API. A resolver wrapper removes the errors of hidden fields and adds the pending async errors, instead of asking each schema to know about visibility. It works for any schema, code or JSON, and keeps schemas plain.
- **Labels are text references.** A code or JSON label is a key of the `forms` namespace (or `ns:key`), or an explicit `{ en, ar }` object. Keys keep the translation tooling working for bundled forms; the object lets a server send text for a form the app has never seen.
- **Drafts are opt in and conservative.** `draft: { key }` saves to encrypted MMKV (`forms.draft.<key>`), never saves a field marked `sensitive` or a file field, and is cleared on a successful submit.
- **The folder follows the repo's structure rules.** Helpers live in `utils/`, hooks in `hooks/`, components in `components/<Name>/`, one `types/index.ts`. The registry is `components/FieldRegistry`.

## Consequences
- A new form is a config and a schema (or a JSON file), not a screen.
- Adding a field type touches the registry in two places (`types.ts` for the props, `FieldRegistry.tsx` for the renderer); the type system points at the second one.
- Validation messages are generic keys without parameters (the `Form*` components translate `error.message` with no options), so "at least 3" is "too short", not "at least 3 characters".
- A server cannot ask for a pattern the app does not have; a project adds the pattern to `utils/patterns.ts` first.
- Drafts hold personal data in the app storage area, which survives sign-out. A project that signs users out should call `discardDraft(key)`.
- Nested repeat sections, and conditions inside repeat items, are not supported in v1.

## Alternatives
- **JSON only (all forms from the server):** needs an expression language for every rule, which is code evaluation by another name, and loses type checking.
- **A JSON Schema form library:** a large dependency, its own validation stack, no use of the `Form*` components.
- **Yup, as in the original:** a second validation library next to Zod for no gain.
- **Visibility inside each schema (`superRefine` with visibility):** couples every schema to the form tree and cannot cover a schema the project already has.
- **Free-form text with keys only:** blocks server-defined forms for screens the app was not built with.
