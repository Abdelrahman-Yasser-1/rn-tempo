<Callout title="Development only" type="warn">
  Tempo Local Backend is a development tool. It answers on your own machine, and the data it keeps is test data. It is not a place to run production traffic or keep real user data.
</Callout>

A **backend** is a folder. The app serves that folder as a real API: HTTPS, a database, sign-in for app users, file uploads, a small CMS and a request log. Your app talks to it like a real server. You change it from a window with eight tabs.

This guide takes you from nothing to the template app logged in against your own backend. Code-defined mocks still live in the [dev API](/docs/backend/dev-api): run them with `yarn api`.

## 1. Install

You do not need Node.js, npm or Yarn to run the app. The engine is built into it.

1. Get the `.dmg`. Open the **Local Backend** run in the repository's **Actions** tab, then download the `tempo-local-backend-dmg` artifact. If a release has a `.dmg`, you can download that instead. The artifact is a `.zip`: unzip it.
2. Open the `.dmg` and drag **Tempo Local Backend** into **Applications**.
3. The first time, right-click the app, choose **Open**, then choose **Open** again. The app is not signed with an Apple developer certificate, so macOS asks once. After that it opens normally.
4. Optional: install [mkcert](https://github.com/FiloSottile/mkcert) with `brew install mkcert`. You need it only for HTTPS, and the next sections use HTTPS.

The `.dmg` is for Macs with Apple silicon. On an Intel Mac, build it from source.

### Or build it from source

You need Node 26 or newer (it builds the engine into one file), Rust 1.85 or newer and Xcode's command line tools.

```sh
yarn install
yarn workspace @rn-tempo/local-backend build:sea        # the engine, as one executable
yarn workspace @rn-tempo/local-backend-app tauri build --bundles app,dmg
```

The `.app` and `.dmg` are in `apps/local-backend/app/src-tauri/target/release/bundle/`. For the window with hot reload, run `yarn workspace @rn-tempo/local-backend-app tauri dev`. Without `build:sea`, `tauri dev` falls back to `node apps/local-backend/engine/dist/cli.mjs` (run `yarn workspace @rn-tempo/local-backend build` first, and have Node 24 or newer).

The same engine runs without the app. See `apps/local-backend/engine/README.md` for `create`, `serve`, `check`, `snapshot` and the rest.

## 2. Create your first backend

1. Open the app and press **New backend**.
2. **Choose a folder.** It must be new or empty. A folder inside your project, such as `backend-local`, is a good place.
3. **Choose what it starts with.**
   - **Tempo template** is ready for the template app: login, profile, 100 products and the rest of its API, with the test user `emilys`.
   - **Empty** has nothing yet. You add collections and endpoints yourself.
4. Optional: change the port. The default is `8443`. If another program uses it, pick a free one, such as `8556`.
5. Press **Create backend**, then press **Start** on the Dashboard.

The dot next to the backend turns green. The Dashboard shows the addresses to use, each with a **Copy** button:

| Address | For |
| --- | --- |
| This Mac | Browsers and `curl` |
| Phone on Wi-Fi | A real phone, with a QR code to scan |
| Android emulator | `10.0.2.2`, the emulator's name for this Mac |
| iOS simulator | `localhost` |

Closing the window keeps the app in the menu bar, where each backend has a Start or Stop entry. **Quit** stops every engine the app started.

## 3. Connect the template app

The template app must trust the backend's certificate, then know its address.

### 3.1 Certificates

1. Open **Settings** and find **Certificates**. Press **Create certificate**. This needs mkcert, and it changes no trust store.
2. Pick your target:
   - **iOS simulator.** Press **Trust on this simulator** next to the booted simulator.
   - **Android emulator.** Press **Send to Android emulator**. The app copies `rootCA.pem` to the emulator's Download folder. Then, on the emulator, open **Settings**, **Security**, **Encryption & credentials**, **Install a certificate**, **CA certificate**, accept the warning and pick the file. Only the `devDebug` build of the template trusts it.
   - **A real phone.** Scan the QR code in Settings with the phone's camera. It opens the public CA file. Install it, then turn on full trust: on an iPhone, in **Settings**, **General**, **About**, **Certificate Trust Settings**.
   - **This Mac's browser.** Press **Trust on this Mac…**. The app asks you to confirm, then macOS asks for your password.
3. Restart the backend after you create or renew the certificate.

See [Local HTTPS](/docs/backend/local-https) for the same steps in a terminal.

### 3.2 Choose the API source

1. In the template app, open the **debug menu** (shake the device, or use the `debug` deep link).
2. Open **API source** and pick **Tempo backend**.
3. Fill in the URL for your target. Use your backend's port (the examples use `8443`):

| Target | URL |
| --- | --- |
| iOS simulator | `https://localhost:8443` |
| Android emulator | `https://10.0.2.2:8443` |
| Real phone | `https://<your Mac's Wi-Fi address>:8443` (the Dashboard shows it) |
| Team server | `https://<host>/b/<name>` (a backend on a [team server](/docs/backend/team-server)) |

### 3.3 Restart the app

Close the template app completely and open it again. The API source applies on the next launch. Later changes to your backend apply live, with no restart.

### 3.4 Log in

On the login screen, use `emilys` and `emilyspass`. The products list and the profile now come from your backend. Open **Logs** in the window to watch the requests arrive.

## 4. Endpoints

An endpoint is one method and path your app can call. Open the **Endpoints** tab. The table shows method, path, type, whether sign-in is needed and a note. Use **Add**, **Edit**, **Duplicate** and **Delete**. The fields of the form change with the type.

| Type | What it does | Example |
| --- | --- | --- |
| Collection | Lists, reads, creates, updates or deletes records of a collection | `GET /products` lists products, with paging and search |
| Fixed answer | Always sends the same status and JSON body | `GET /app-config` answers `{ "minVersion": "1.2.0" }` |
| Sign-in | One step of the login flow | `POST /auth/login` checks a password and returns tokens |
| Users | Adds, updates or reads an app user | `GET /users/me` returns the signed-in user |
| File upload and download | Receives files, or sends one | `POST /media` stores an upload |
| Custom code | Runs your own JavaScript file | `GET /stats/summary` counts products and users (see step 11) |

**Scenarios.** Every endpoint has a scenario picker: a slow answer, a server error, an empty body and so on. Pick one and the next request gets that answer. This is how you see your app's error screens without breaking anything.

**Try it.** Press **Try it** to send a real request through the app. The **Log in as…** picker lists your app users and fills in a bearer token for you.

Saving goes through the engine, which reloads at once.

### 4.1 Import an OpenAPI or Swagger file

If your API already has a description file, import it instead of writing each endpoint. The engine reads **OpenAPI 3.0 and 3.1** and **Swagger 2.0**, as JSON or YAML.

**From the dashboard.** In the **Endpoints** tab choose **Import API file…**. In the desktop app the app opens a file dialog. In the browser you choose a file or drop it on the dialog. You can also paste an address (**From URL**). A review screen shows the endpoints per tag and any warnings. Choose **Apply** to make the endpoints.

**From a terminal.** The command creates the backend folder when it does not exist, and updates it when it does:

```bash
npx @rn-tempo/local-backend import ./backends/pets --openapi ./petstore.yaml
npx @rn-tempo/local-backend import ./backends/pets --openapi https://example.com/openapi.json --preview
```

`--preview` only prints what would change. Without a choice screen, the command adds new endpoints, takes changes to endpoints you never edited, keeps the ones you edited, and deletes nothing.

**What you get.** Each operation becomes one fixed-answer endpoint:

- The id is the `operationId`, or the method and path when there is none (`get.pets.:petId`). Tags and the summary are kept, and `{petId}` becomes `:petId`.
- **Each documented response is a scenario**, named after its status and description (`200 aListOfPets`, `404 notFound`, `422 validationFailed`). The first 2xx response is the normal answer. Pick another with the scenario picker, or the `x-tempo-scenario` header: `curl -H 'x-tempo-scenario: 404 notFound' ...`.
- **Response bodies** come from the file's `example` or `examples`. When there is none, the engine generates data from the schema: emails, UUIDs, dates, URLs, enums, number limits and arrays of 1 to 3 items. The data is the same every time you import the same file.
- **Requests are checked.** A request whose path parameters, query or JSON body do not match the schema gets `400` with the names of the wrong fields (`body.name`, `query.limit`). A scenario you pick replaces the answer without the check.
- **Sign-in.** An operation with a bearer, OAuth 2 or API key requirement needs a bearer token. API keys and basic authentication are not supported, so they become bearer and a warning says so.
- **Swagger 2.0** is converted in the engine itself: `definitions`, body, form, query, path and header parameters, response `schema` and `examples`, `consumes` and `produces`, `securityDefinitions`, and `host`, `basePath` and `schemes`.
- **Base path.** A new backend takes the path of the file's first server (`/api/v1`) as its base path.

**Warnings** list what was skipped: callbacks, links, webhooks, `HEAD`, `OPTIONS` and `TRACE`, paths that mix text and a parameter in one segment (`/files/{name}.json`), recursive references (cut to "any"), request bodies that are not JSON, and header parameters (documented, not checked). Regular expressions (`pattern`) in schemas are removed, because a pattern from a file runs against whatever callers send and could be made to run for a very long time. A file whose references fan out into more than 200 000 schema nodes is refused.

**Import again, and review the diff.** `backend.json` records each import (`imports`) and a fingerprint of every endpoint as the import made it (`importedFrom`). Import the changed file again and the review screen lists:

| Group | Meaning |
| --- | --- |
| Added | In the file, not in the backend yet. Default: add. |
| Changed | The file differs. The list says what: request body, a response schema, a new scenario... Default: take the new one, or keep yours when you edited it. |
| Removed | Made by an earlier import, but not in the file now. Default: keep (nothing is deleted unless you choose it). |
| Unchanged | The same as before. |

An endpoint you edited after the import is marked **you edited it**. For each changed endpoint choose:

- **Take the new one** replaces it with the file's version.
- **Keep mine** leaves it as it is. The same file is not offered again as a change.
- **Merge** adds the file's new scenarios and updates the schemas, and keeps your response bodies, statuses, headers and delays.

Endpoints you made yourself are never listed as removed. A new operation whose method and path another endpoint already answers is left out, and the screen says so. Importing a second, different file into a backend lists the first file's endpoints under "not in the file any more"; they stay unless you choose to delete them.

**An address.** Only `https:` addresses (and `http:` for localhost) are fetched, at most 10 MB, within 15 seconds and after at most 3 redirects, each one checked again. On a [team server](/docs/backend/team-server) a name or address on a private network (localhost, `10.x`, `192.168.x`, link-local) is refused, so the server cannot be used to reach the network it runs in. Upload the file instead, or start the server with `--allow-private-import-urls` for a team that keeps its API descriptions on a LAN. Only the address without user name, password, query and fragment is recorded in `backend.json` and in the audit log.

On a team server, previewing and importing need the **editor** role, and both are written to the audit log.

### 4.2 Delays and network presets

Make the backend as slow as a real connection. Set it for the whole backend in **Settings, Network**, or for one endpoint in its form under **Speed**.

| Preset | Delay | Download | Upload |
| --- | --- | --- | --- |
| Instant | none | no limit | no limit |
| Fast Wi-Fi | 20 ms | 30 Mbps | 15 Mbps |
| 4G | 60 ms | 9 Mbps | 1.5 Mbps |
| Slow 3G | 400 ms | 500 kbps | 500 kbps |
| Timeout | holds the request, then closes the connection without an answer (30 s, or your `timeoutMs`) | | |
| Custom | only the speeds you type | | |

4G and Slow 3G use the numbers of Chrome DevTools' "Fast 4G" and "Slow 3G" profiles. Fast Wi-Fi is a typical home connection, not a DevTools profile.

The same settings in `backend.json`:

```json
{
  "latency": { "default": { "minMs": 100, "maxMs": 900 } },
  "network": { "preset": "4g" },
  "endpoints": [
    { "id": "get.slow", "type": "static", "method": "GET", "path": "/slow", "latency": { "fixedMs": 2000 }, "network": { "preset": "custom", "downloadKbps": 200 } }
  ]
}
```

Which delay wins, first match: a scenario's `delayMs`, the endpoint's `latency`, the backend's `latency.default`, then the preset's own delay. An endpoint's `network` replaces the backend's. `"inherit"` (the default) uses the backend's.

- A **random range** picks a value for each request from a generator seeded by the request number, so a run can be repeated. The **Logs** detail shows what was applied, for example "delayed 734 ms (default), download 500 kbps".
- **Throttling** sends response bodies, including media downloads, in small pieces at the set speed, and reads request bodies at the set upload speed. Everything stops at once when the app disconnects.
- A request that times out shows as **closed** in the log.

**Test mode** turns every delay, speed limit and timeout off, and fixes `{{now}}` and the random values. Turn it on for a whole backend (`"testMode": true`, or the checkbox in Settings), for the engine (`local-backend-engine serve <dir> --test-mode`), or for one request with the header `x-tempo-test-mode: 1`. Send `x-tempo-test-delays: 1` as well to keep the configured delays anyway, for a test that is about slowness.

### 4.3 A shared response shape and templates

In **Settings, Responses** (or `responses` in `backend.json`) you can give every answer the same shape.

```json
{
  "responses": {
    "success": { "success": true, "data": "{{body}}", "message": null },
    "error": { "format": "custom", "template": { "success": false, "code": "{{status}}", "message": "{{message}}", "details": "{{errors}}" } },
    "headers": { "x-api-version": "2" }
  }
}
```

- **Success wrapper.** The string `"{{body}}"` (the whole string) is replaced by the endpoint's body and keeps its type, so arrays and objects stay as they are. Only success answers with a JSON body are wrapped; errors, empty answers and file downloads are not.
- **Error format.** `problem` (the default, `application/problem+json`), `dummyjson` (`{ "message": "..." }`) or `custom` with your own template that receives `{{status}}`, `{{message}}` and `{{errors}}`. It applies to errors the engine makes: validation (400), sign-in (401), not found (404), wrong method (405) and rate limits (429). An error body you wrote yourself in a scenario is sent as written.
- **Common headers** are added to every answer. An endpoint's `headers` win over them, and a scenario's win over both.
- **Per endpoint.** `wrap` is `"inherit"` (the default), `"none"` or the name of a template. The OpenAPI document and the contract check describe the wrapped shape.
- The **Tempo template** preset sets `"wrap": "none"` on every endpoint, so its answers match the template's contract even if you add a wrapper later.

A **response template** is a response you reuse:

```json
{
  "responseTemplates": { "gone": { "status": 410, "body": { "message": "{{with.message}}" } } },
  "endpoints": [
    { "id": "get.old", "type": "static", "method": "GET", "path": "/old", "body": { "template": "gone", "with": { "message": "Use /new" } } }
  ]
}
```

A body that is exactly `{ "template": "name" }` or `{ "template": "name", "with": { ... } }` uses the template. The template's `status` applies when the endpoint or scenario leaves its own unset (for an endpoint: at the default 200). Pick one in the endpoint form with **Use template**.

Order of work for one answer: the endpoint's body (a template is expanded and dynamic values filled), then the wrapper, then the headers. Changing these settings needs the admin role on a team server, and is recorded in the audit log.

### 4.4 Dynamic values

Static bodies, scenario bodies, template bodies and header values can hold `{{...}}` values. Press **Dynamic values** in the endpoint form for the list.

| Value | Meaning |
| --- | --- |
| `{{params.id}}`, `{{query.q}}` | A path parameter, a query value (text) |
| `{{body.user.name}}` | A value of the JSON request body (keeps its type) |
| `{{headers.x_request_id}}` | A request header (`_` reads `-`). Never `authorization` or `cookie` |
| `{{user.id}}`, `{{user.username}}` | The signed-in app user, on endpoints that need sign-in |
| `{{now}}`, `{{now.iso}}`, `{{now.unix}}` | The time as ISO text, and as seconds |
| `{{uuid}}`, `{{seq}}` | A new id, and a counter of this endpoint's requests (the same inside one answer) |
| `{{random.int 1 100}}` | A whole number in a range |
| `{{fake.name}}`, `{{fake.email}}`, `{{fake.sentence}}` | Made-up text |
| `{{with.x}}` | In a template: a value passed with `with` |

The rules:

- **No code is run.** A small tokenizer cuts out `{{ ... }}` and looks the name up in a fixed list. A path has only letters, digits and `_` segments, and `__proto__`, `constructor` and `prototype` are refused. Expressions such as `{{1+1}}` are not understood and give a missing value.
- **Types.** A string that is only one value keeps the value's type: `"{{body.n}}"` is a number when `n` is. Inside other text (`"id-{{params.id}}"`) a value becomes text. Path and query values are text, so write `{{params.id | number}}` to get a number (the only filter).
- **Missing values** are `null` on their own and empty inside text. They never cause an error.
- **Escape** with a backslash: `\{{` writes a literal `{{` (in JSON, `"\\{{"`).
- The answer may not grow past 1 MB after filling; the engine then answers 500 and says why. Stored data (collections, content) is never filled in.
- In **test mode** `{{now}}` is fixed (`2025-01-01T00:00:00.000Z`), and `{{uuid}}`, `{{random...}}` and `{{fake...}}` are seeded, so the same requests give the same values. `{{seq}}` starts again after a reset.

### 4.5 The JSON editor

Bodies, scenarios, templates, the success wrapper, **Try it** bodies and JSON fields of data rows and content entries open in an editor with two tabs.

- **JSON** is a code editor (Monaco) with formatting (**Format**, or Shift+Alt+F), folding, find and replace (Ctrl or Cmd+F, Ctrl or Cmd+H), a **Minimap** switch, a light or dark theme that follows the system, and **Show changes**, a side by side diff against the last saved text. When an imported file or the collection describes the shape, the editor checks against it and suggests fields. `{{...}}` values are coloured and never flagged, even where a number is expected.
- **Form** is made from the same schema (or from the value, when there is none) and edits the same text. Switching tabs keeps your edits. Switching to the form needs valid JSON, and says what to fix.

The editor is bundled with the app, works offline and loads only the first time one opens, so the dashboard starts as fast as before.

### 4.6 Live data: SSE, WebSocket and GraphQL

Three more endpoint types keep a connection open or speak GraphQL. All of them read the **data change events** of the backend: whenever a record is created, updated or deleted (by an endpoint, the Data tab, a handler or the test kit), the event `<collection>.created`, `<collection>.updated` or `<collection>.deleted` is published after the change is saved, with `{ collection, id, record }` (a delete carries the record as it was). Publishing or unpublishing a content entry publishes `content.published` or `content.unpublished`, and a handler publishes its own with `ctx.emit(name, payload)`. Fields that a collection endpoint hides are left out of the events too.

In an endpoint's list, list events with `on`: a name (`products.created`), a prefix (`products.*`) or `*`.

Each of these endpoints has a **Live** button in the Endpoints tab. It shows who is connected (a client id, when it connected, how many messages went each way, and a short hash of the address, never the address), the latest messages, a form that sends a message to everyone or to one client, and **Disconnect**. Viewers can read the panel; sending and disconnecting need the editor role on a team server.

#### Server-sent events (SSE)

Choose **Live events (SSE)**. The endpoint answers `GET` with `text/event-stream`.

| Setting | What it does |
| --- | --- |
| `script` | Messages sent, in order, to every client that connects: `{ "event": "hello", "data": { "n": "{{seq}}" }, "delayMs": 500, "repeat": 3 }`. `data` is sent as text, or as JSON when it is not text; placeholders are filled for every message, and `{{seq}}` counts the messages of that connection. |
| `on` | Data change events to forward. A forwarded message has `event: products.created` and the payload as JSON in `data`. |
| `retryMs` | The `retry:` hint, how long a client waits before reconnecting (default 3000). |
| `heartbeatMs` | A comment line this often keeps proxies from closing a quiet stream (default 15000, 0 turns it off). |
| `idleTimeoutMs` | A client that gets no message for this long (heartbeats do not count) is closed (default 30 minutes, 0 turns it off). |
| `maxConnections`, `maxConnectionsPerIp` | The next client past the limit gets `429` (default 100 and 10). |
| `bufferSize` | How many forwarded and broadcast messages are kept for `Last-Event-ID` (default 100). |

Messages are real SSE: `id`, `event`, one `data:` line per line of text, `retry`. A client that reconnects with `Last-Event-ID` gets the messages it missed from the buffer instead of the script again. `auth: "bearer"` needs a token in the `Authorization` header. In test mode every `delayMs` is 0 and the order of the messages stays the same.

```bash
curl -N https://localhost:8443/events
```

From React Native, `EventSource` does not exist, so add a polyfill. Both of these read the same stream:

```ts
import EventSource from 'react-native-sse';

const source = new EventSource('https://192.168.1.20:8443/events', {
  headers: { Authorization: `Bearer ${token}` },
});
source.addEventListener('products.created', (event) => {
  const { record } = JSON.parse(event.data ?? '{}');
  console.log('new product', record.title);
});
// Close it when the screen goes away: source.close()
```

#### WebSocket

Choose **Live socket (WebSocket)**. The endpoint answers the HTTP Upgrade on its path (a plain `GET` answers `426`). The engine uses the `ws` library, because Node has a WebSocket client but no server.

| Setting | What it does |
| --- | --- |
| `behavior` | `echo` sends every message back. `rules` answers with the first rule that matches (and says nothing when none does). |
| `rules` | `{ "match": { ... }, "reply": ..., "delayMs": 200, "broadcast": true }`. `reply` is sent as text, or as JSON when it is not text. `{{message.user.name}}` reads a field of the message and `{{message}}` is the whole message. `broadcast` sends the reply to every connected client. |
| `onConnect` | A welcome message sent when a client connects. |
| `on` | Data change events to forward, sent as `{ "event": "products.created", "data": { ... } }`. |
| `subprotocols` | The subprotocols the endpoint speaks. The first one the client offers is chosen. |
| `maxPayloadBytes` | The largest message (default 64 KB). A client that sends more is closed with 1009. |
| `maxConnections`, `maxConnectionsPerIp` | Past the limit the upgrade gets `429`. |
| `pingIntervalMs` | A ping this often. A client that never answers the last one is dropped (default 30 seconds). |
| `maxBufferedBytes` | A client with more than this waiting to be sent is too slow and is closed with 1013 (default 1 MB). |

A rule matches when **every** condition it lists fits: `type` (the message is JSON with this `type`), `jsonPath` (`$.user.name`, `$.items[0].id`, `$['a b']`; alone it means the value exists), `equals` (the value at `jsonPath`, or the whole message, is equal to this), `contains`, `startsWith` and `endsWith` (text). Regular expressions are not supported on purpose: a pattern written in `backend.json` runs on whatever a client sends, and a crafted one can freeze the server (ReDoS). Every condition above takes time proportional to the message.

**Signing in.** With `auth: "bearer"`, send the token one of three ways. The first is best, because a URL ends up in proxy logs.

1. In the subprotocol: `new WebSocket(url, ['bearer', token])`. The engine answers with `bearer`, never with the token.
2. In the `Authorization` header, where the client can set one (React Native can: `new WebSocket(url, null, { headers })`).
3. In the URL: `wss://host/ws?token=<token>`. The engine hides a `token` in the request log.

Under a team server the same endpoint is at `wss://<server>/b/<backend>/ws` and, in a CI session, at `wss://<server>/s/<session>/ws`. Caddy's `reverse_proxy` passes upgrades and event streams on as they are, so the compose file needs no change.

```ts
const socket = new WebSocket('wss://192.168.1.20:8443/ws', ['bearer', token]);
socket.onopen = () => socket.send(JSON.stringify({ type: 'ping' }));
socket.onmessage = (event) => {
  const message = JSON.parse(String(event.data));
  if (message.event === 'products.created') console.log(message.data.record.title);
};
```

The request log shows a `WS` row for the connection (status 101), one for each message (200, the text cut and secrets replaced) and one when it closes.

#### GraphQL

Choose **GraphQL**. It answers `POST` at its path (default `/graphql`), built with the reference `graphql` package.

- **Built from my collections.** For a collection `products` you get the type `Product`, the query `products(limit, skip, where, sort)` and `productsById(id)`, the mutations `createProduct`, `updateProduct` and `deleteProduct`, and the subscriptions `productsCreated`, `productsUpdated` and `productsDeleted`. Enum fields become enums, `json` fields use a `JSON` scalar, and fields that a collection endpoint hides are left out (hide more with `schema.hiddenFields: ["products.secret"]`; limit the collections with `schema.collections`).
- **Written by me (SDL).** Put the schema in `schema.sdl`. Every field is null unless `resolvers` names what answers it: `{ "Query.hello": { "static": "Hello {{args.name}}" } }`, `{ "Query.items": { "collection": "products", "action": "list" } }`, `{ "Query.x": { "handler": "handlers/x.js" } }` (the handler gets `ctx.req.body = { field, args, parent }` and returns the value) or, for a subscription, `{ "Subscription.shipped": { "event": "orders.shipped" } }`.
- **Generate from collections** in the endpoint form writes the generated schema and its resolvers out as text, so you can edit them. With the built-in schema, `schema.sdl` can also hold extra types (`extend type Query { hello: String }`).

| Setting | What it does |
| --- | --- |
| `maxDepth` | The deepest query allowed (default 10). Introspection is not counted. |
| `maxFields` | The most fields a query may select, with every use of a fragment counted again (default 200). |
| `maxQueryBytes` | The longest query text (default 20 KB, `413` beyond). |
| `introspection` | Answer `__schema` and `__type` (on by default, because this is a mock). |
| `requireAuth` | Operations that need a signed-in user, such as `Mutation.createProduct`. `auth: "bearer"` protects every operation. |

Batching is not supported (an array body answers 400). A query that is too deep or too big is refused before it runs, and fragment cycles cannot loop. The answer is `{ data, errors }` and is never put inside the backend's success wrapper. The request log and the stats keep the operation name (`query ListProducts {...}` shows as `ListProducts`; an unnamed one as `anonymous`). OpenAPI lists the endpoint as a `POST` with a generic body, marked as GraphQL.

**Subscriptions** use a WebSocket on the same path with the `graphql-transport-ws` subprotocol (the graphql-ws protocol): `connection_init`, `subscribe`, `next`, `complete`, ping and pong, and its close codes (`4401` before init, `4408` init timeout, `4409` duplicate id, `4429` second init, `4403` forbidden). The engine implements this small subset itself, because the `graphql-ws` package would take over the socket, its limits and the request log. With `auth: "bearer"` a client signs in with `connection_init`'s payload (`{ "Authorization": "Bearer <token>" }`), the subprotocol pair or `?token=`.

There is no GraphiQL page: it would have to load scripts from a CDN, which the engine never does. The **Query** button in the Endpoints tab opens a small query runner in the dashboard instead (query, variables, operation name, and **Log in as** an app user). Point Apollo, urql or `fetch` at the URL:

```ts
import { ApolloClient, HttpLink, InMemoryCache, split } from '@apollo/client';
import { GraphQLWsLink } from '@apollo/client/link/subscriptions';
import { getMainDefinition } from '@apollo/client/utilities';
import { createClient } from 'graphql-ws';

const http = new HttpLink({ uri: 'https://192.168.1.20:8443/graphql' });
const ws = new GraphQLWsLink(
  createClient({
    url: 'wss://192.168.1.20:8443/graphql',
    connectionParams: { Authorization: `Bearer ${token}` },
  }),
);
const link = split(
  ({ query }) => {
    const definition = getMainDefinition(query);
    return definition.kind === 'OperationDefinition' && definition.operation === 'subscription';
  },
  ws,
  http,
);
export const client = new ApolloClient({ link, cache: new InMemoryCache() });
```

With urql, use `createClient({ url, exchanges: [cacheExchange, fetchExchange, subscriptionExchange({ forwardSubscription })] })` and a `graphql-ws` client in `forwardSubscription`; both clients speak the same protocol.

### 4.7 Webhooks

A webhook calls a URL when an event happens: a record is created, changed or deleted (`products.created`, `products.updated`, `products.deleted`, `products.*`, `*`), content is published (`content.published`), or a handler calls `ctx.emit('orders.shipped', { ... })`. Add them in **Settings → Webhooks**, or in `backend.json`:

```json
{
  "webhooks": [
    {
      "id": "orders",
      "url": "http://localhost:8557/hook",
      "events": ["products.created", "custom.*"],
      "delayMs": 0,
      "retries": { "max": 3, "backoff": "exponential", "baseMs": 1000 },
      "headers": { "x-env": "dev" },
      "body": { "text": "New {{event.data.record.title}}" }
    }
  ]
}
```

- **Body.** Without `body` it is `{ "id", "event", "createdAt", "data" }`. With a template, `{{event.id}}`, `{{event.name}}`, `{{event.createdAt}}` and `{{event.data.<path>}}` are filled in. Fields an endpoint hides are not sent.
- **Signing.** Every call has `X-Tempo-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "t.body">` (like Stripe), `X-Tempo-Event` and `X-Tempo-Delivery`. The signing secret is made per webhook, is **shown once** when you create the webhook (or rotate it, which needs the admin role), and lives only in `.data/secrets.json`. Verify it in your receiver:

  ```js
  import { createHmac, timingSafeEqual } from 'node:crypto';
  const [t, v1] = header.split(',').map((part) => part.split('=')[1]);
  const expected = createHmac('sha256', secret).update(`${t}.${body}`).digest('hex');
  const ok = timingSafeEqual(Buffer.from(v1), Buffer.from(expected));
  ```

- **Delivery.** 10 second timeout. A failure (a network error or a status outside 2xx) is retried with exponential backoff and up to 20% jitter, at most 5 minutes apart. Pending deliveries are stored in the database, so a restart continues them. The log (status, duration, response code, the first 2 KB of the answer, attempt number) is kept 7 days. **Redeliver** sends a delivery again, and **Send test** sends a `webhook.test` event.
- **Test mode.** No delays, deterministic ids, and nothing is sent: the test kit captures each delivery. `backend.webhooks.deliveries()` returns `{ id, webhookId, event, url, headers, body, json }`, signed as it would have been.
- **Safety.** Redirects are not followed. On a team server the URL must be `https:` and may not point at the local machine or a private network (the same rule as importing an API file from a URL; the owner can allow private addresses with `--allow-private-import-urls`). On your own machine `http://localhost` is fine. The webhook list hides header values and query values; the secret is in no export, snapshot, log or answer.

### 4.8 Inbox: capture what a service sends you

Add an endpoint of type `inbox` (for example `/inbox/stripe`) and point a service at it. It answers `200 { "received": true }` (set `status` and `body` to change that, and a latency as for any endpoint), accepts **any method**, and keeps the headers, query and the raw body (up to 1 MB, otherwise 413). The newest 500 per endpoint are kept, with a total size cap.

```json
{ "id": "stripe.inbox", "type": "inbox", "path": "/inbox/stripe", "status": 200 }
```

The **Inbox** tab lists captures (time, method, path, size, status). Editors open one to see the headers, the query and the body (pretty JSON in a read-only editor, or raw), copy it as a `curl` command, **replay** it to another URL (through the same safety rules as webhooks), or clear the inbox. Credentials are hidden before anything is stored: any header or query parameter whose name has `auth`, `token`, `key`, `secret`, `session`, `cookie`, `credential` or `password` is replaced, and signature headers keep only their last four characters. The request log shows the length of an inbox body, never the body.

### 4.9 Push notification test sender

**Settings → Push** sends a test push to a real device token from your Mac. Both senders keep their credentials in `.data/secrets.json` (never in `backend.json`, exports, snapshots, logs or answers). The page shows only "Configured" and the project or key id. Needs the admin role on a team server.

- **FCM (HTTP v1).** Upload a service account JSON (Firebase console, Project settings, Service accounts, Generate new private key). The engine signs an RS256 JWT with it, exchanges it at `oauth2.googleapis.com` for an access token (cached until it is about to expire) and posts the message to `fcm.googleapis.com/v1/projects/<project>/messages:send`.
- **APNs.** Upload the `.p8` key and give its key id, your team id and the app's bundle id. The engine signs an ES256 provider token (reused for under 50 minutes) and calls `api.sandbox.push.apple.com` (the **Sandbox** toggle, for development builds) or `api.push.apple.com` over HTTP/2 with `apns-topic`, `apns-push-type` and `apns-priority`.
- **Send test.** Choose the platform, paste the device token, give a title and body (or neither, for a silent data push) and optional data JSON. The result shows the provider's status and reason (`UNREGISTERED`, `BadDeviceToken`...). The last 50 sends are kept with the token masked.

**Owner check on a real device (AC-LP-9).** The automated tests use generated keys and fake network layers, so a real delivery is yours to confirm:

1. Run the app on a physical phone with push set up, and read its device token (FCM registration token, or the APNs token as hex).
2. Upload the credentials in Settings → Push (for APNs a development build uses the sandbox).
3. Send a test with a title and body. The phone should show the notification, and the result should read status 200.
4. Check that the credentials appear nowhere else: not in `backend.json`, not in an exported backup, not in `.data/logs`.

### 4.10 Faults and limits

**Settings → Faults, CORS and sessions** (or `faults` in `backend.json`, for the whole backend or one endpoint; an endpoint's setting replaces the backend's) simulates trouble:

| Setting | Effect |
|---|---|
| `rateLimit: { requests, perSeconds, key }` | More than `requests` in `perSeconds` answers **429** with `Retry-After`. `key` is `ip`, `user` or `global`. `null` on an endpoint turns the backend's limit off. |
| `failureRate` (0 to 1), `failureStatus`, `failureBody` | That share of requests fails before reaching the endpoint (status 500 by default). |
| `dropRate` | That share of answers are cut: the head and half the body are sent, then the connection is destroyed. |
| `offline: true` | Every connection is closed at once. |
| `slowUpload`, `slowDownload` | Kilobits per second (the same throttle as network presets). |

Rate limit answers carry the IETF `RateLimit` headers: `RateLimit: limit=…, remaining=…, reset=…` and `RateLimit-Policy`, plus the older `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` that many clients still read. Windows are fixed, starting at a key's first request.

**Repeatable.** Random choices are drawn from a generator seeded with the request number and the engine's seed (fixed in test mode and in the test kit), so the same run fails on the same requests. **Test mode.** Faults are **off** in test mode unless a request sends `x-tempo-test-faults: 1` (the engine exports the name as `TEST_FAULTS_HEADER`), like `x-tempo-test-delays: 1` for delays. The dashboard and `GET /stats` show how many requests were rate limited, failed, dropped or refused offline.

### 4.11 CORS and cookie sessions

**CORS.** Without a `cors` setting no CORS headers are sent, as before: a web page on another origin cannot read the API (native apps are not affected). Set it to let a web app call the backend:

```json
{ "cors": { "origins": ["https://app.example.com"], "methods": ["GET", "POST"], "credentials": true, "maxAge": 600 } }
```

`origins` is `"*"` or a list; the matching origin is echoed with `Vary: Origin`. Preflight (`OPTIONS` with `Access-Control-Request-Method`) is answered with 204, before any access key check. `"*"` with `credentials: true` is refused, as browsers refuse it.

**Cookie sessions.** `auth.mode` is `bearer` (default), `cookie` or `both`. In cookie mode, login sets `tempo_app_session` (`HttpOnly; SameSite=Lax; Path=<base path, or /b/<id>/ on a team server>`, `Secure` over HTTPS) and, in the answer, a `csrfToken` (also in the `tempo_app_csrf` cookie, readable by scripts). Endpoints with `auth: "bearer"` then accept the cookie, and logout clears it. In `cookie` mode the answer carries no access token, so scripts never hold one.

- **CSRF.** A request that is signed in by the cookie and uses POST, PUT, PATCH or DELETE needs either the `x-tempo-csrf` header with the login's `csrfToken` (double submit), or an `Origin` that is the server itself or one of `cors.origins` (and not `Sec-Fetch-Site: cross-site` unless listed). Otherwise it gets 403. Native mobile apps send no `Origin`, so they send the header. Requests with a bearer token need none.
- **Why Lax.** `SameSite=Lax` keeps the cookie when the user is sent back from another site, which OAuth redirects need (`Strict` would drop it). The CSRF check above covers what Lax lets through.
- **Team server.** A backend can never set a cookie there, unless its mode is cookie: then only `tempo_app_session` and `tempo_app_csrf`, with `Path=/b/<id>/` and no `Domain`, are passed on, and the dashboard's own cookie name is never used.

### 4.12 OAuth 2.0 / social login mock

**Settings → OAuth sign-in mock** (or `oauth` in `backend.json`) makes the backend an OAuth 2.0 and OpenID Connect provider for its app users:

```json
{ "oauth": { "enabled": true, "provider": "google", "clients": [{ "clientId": "my-app", "redirectUris": ["myapp://callback"] }] } }
```

| Address | What |
|---|---|
| `GET /oauth/authorize` | A plain page (strict content security policy, no scripts, sandboxed) that lists the app users and **Deny**. It redirects only to a registered `redirectUris` entry, compared exactly. |
| `POST /oauth/token` | `authorization_code` with **PKCE S256 required**, and `refresh_token`. Codes work once and expire after 60 seconds. |
| `GET /oauth/userinfo` | The user's claims, with `Authorization: Bearer <access_token>`. |
| `GET /.well-known/openid-configuration`, `GET /oauth/jwks` | Discovery and the key for the RS256 `id_token` (the private key is in `.data/secrets.json`). |

The `provider` picks the claim names: `google` (`sub, email, email_verified, name, given_name, family_name, picture`), `apple` (`sub, email, email_verified, is_private_email`, as strings) or `github` (`id, login, name, email, avatar_url`); `generic` gives `preferred_username`. The access and refresh tokens are the backend's own, so they also work on `auth: "bearer"` endpoints. A client is public by default; make a **client secret** (shown once, kept in secrets) and the token endpoint then requires it. Clients and secrets are managed by admins.

Not implemented: the implicit and password grants, `plain` PKCE, a consent screen, scopes beyond `openid profile email`, introspection, revocation, dynamic client registration and key rotation.

With `react-native-app-auth`:

```ts
import { authorize } from 'react-native-app-auth';

const result = await authorize({
  issuer: 'https://localhost:8443', // or https://<server>/b/<id> on a team server
  clientId: 'my-app',
  redirectUrl: 'myapp://callback',
  scopes: ['openid', 'profile', 'email'],
  usePKCE: true,
});
```

### 4.13 Security notes for these features

- Secrets (webhook signing secrets, FCM and APNs credentials, OAuth client secrets and the id token key) live only in `.data/secrets.json`, mode 0600. They are in no `backend.json`, snapshot, test snapshot, export, log, audit entry or answer. A webhook secret is keyed by the webhook's own id, so no setting can point at another webhook's secret.
- Everything the engine calls on your behalf (webhook URLs, inbox replays) goes through the SSRF guard: no redirects, the connection goes to the address that was checked, and a team server refuses private, loopback and link-local addresses and plain `http:`.
- Captured inbox bodies are kept as received because you need to see them. Only editors read them, and the list and the request log never show them.
- Settings that change how the backend is reached (faults, CORS, the session mode, OAuth) need the admin role on a team server.

## 11. Custom code handlers

Use a handler when no other endpoint type fits. Choose the **Custom code** type in an endpoint, then press **Create file from example**. The app writes `handlers/<name>.js`. Edit it in your editor. Saving the file reloads it, so the next request runs the new code.

An example, `handlers/stats-summary.js`:

```js
// GET /stats/summary: how many products and users exist.
export default async function (ctx) {
  const products = await ctx.db.count('products');
  const users = await ctx.users.count();
  ctx.log.info('stats summary', { products, users });
  return { products, users };
}
```

What `ctx` has:

| Part | What it gives you |
| --- | --- |
| `ctx.req` | `method`, `path`, `params`, `query`, `headers`, `body` and `user` (the signed-in user) |
| `ctx.db` | `list`, `get`, `count`, `create`, `update`, `delete` on your collections. There is no raw SQL. |
| `ctx.users.count()` | How many app users exist |
| `ctx.media` | `get(id)` and `url(id)` |
| `ctx.emit(name, payload)` | Publishes a custom event (see [Live data](#46-live-data-sse-websocket-and-graphql)) that SSE and WebSocket endpoints and GraphQL subscriptions can listen to |
| `ctx.log` | `debug`, `info`, `warn`, `error`, written to the engine log with secrets hidden |
| `ctx.scenario` | The scenario picked for this endpoint |

What you return becomes the answer. Return a plain value for a 200, or `{ status, headers, body }` to choose them.

The **timeout** is set on the endpoint (5 seconds by default, 30 at most). A handler that runs longer is stopped, and the app gets a 504. The engine keeps serving.

<Callout title="Trusted code, not a sandbox" type="warn">
  A handler runs on your Mac with your permissions. It can read files, use the network and start programs. Only open backends whose `handlers/` folder you trust.
</Callout>

## 12. What to commit

Commit these:

- `backend.json`: collections, endpoints, settings
- `handlers/`: your custom code
- `seed/`: the starting data

Never commit `.data/`. It holds the database, uploaded files, secrets, certificates and logs. The backend writes its own `.gitignore` inside `.data/`, so Git skips it. Do not remove that file. To share a backend with its data, use **Export backup…** instead.

## 13. Troubleshooting

**The port is in use.** The Dashboard says so and offers **Try another port**. Or stop the other program, or set another port in **Settings**, then **Restart now**. The program on port `8443` may be a dev API you started with `yarn api up`.

**Certificate errors.** The target does not trust the certificate yet. See step 3.1 for the target, then restart the template app.

| Target | Message | Fix |
| --- | --- | --- |
| iOS simulator | error -1202, "server certificate is untrusted" | Press **Trust on this simulator**. On a real iPhone, turn on **Certificate Trust Settings**. |
| Android emulator | "Trust anchor for certification path not found" | Install the CA from Settings and run the `devDebug` build. |
| Browser | `ERR_CERT_AUTHORITY_INVALID` | Press **Trust on this Mac…** |
| Only the Wi-Fi address fails | The certificate was made for another address | Create the certificate again, then restart the backend. |

**"No internet connection" in the app.** The template shows this when a request fails before it reaches a server. A common cause is a comment on the same line as a value in `.env.dev`:

```ini
API_BASE_URL=https://localhost:8443  # my backend
```

The comment becomes part of the address, so every call fails. Put comments on their own line. The same message appears when the backend is stopped, when the address is wrong for the target (`localhost` does not work on the Android emulator: use `10.0.2.2`), or when the certificate is not trusted.

**The app does not see my changes.** Changes to endpoints, data and handlers apply live: the next request sees them. Changing the **API source** in the debug menu needs a restart of the template app. A new certificate or port needs a restart of the backend.

**The engine will not start.** The Dashboard shows its last lines. A message that the bundled engine is missing means the app is damaged: install it again.

To test with a throwaway certificate authority, start the app with `CAROOT` set to a temporary folder. It is passed to mkcert, so your real CA is untouched.

## 14. Security model

- **No Node.js needed.** The engine is a single executable inside the app. The app runs that file and nothing else.
- **Two listeners.** The API listens on all interfaces, so a phone can reach it. The admin API that the window uses listens only on `127.0.0.1`, on a random port, and wants a token that is new at every start. The public port answers 404 for every admin route.
- **The token never reaches the window.** The engine prints it once, to the app. Rust keeps it and adds it to each admin call. The window has no token, no URL of the admin port and no way to make a request itself.
- **Fixed commands.** Rust runs a closed set: start and stop an engine, `create`, `certs`, `trust` for this Mac, a simulator or Android, `snapshot` and `check`, plus `xcrun simctl list` to find simulators. The window cannot pass a program or an argument, and it can only act on backends you opened.
- **Certificates stay on.** "Try it" calls go through Rust, which trusts only this backend's own `rootCA.pem`. Verification is never switched off, and the app never changes a trust store unless you press a Trust button and confirm.
- **Files.** Folder and file dialogs open from Rust, so the window never names a path (dropped files are kept by Rust too). Writes use a fresh temp file and refuse symbolic links. Reveal shows a plain file or folder inside the backend in Finder with `open -R`, and never launches it.
- **A strict content security policy.** Scripts and styles only from the app itself, no remote content and no telemetry. Media previews come from `blob:` URLs made from bytes Rust fetched after it checked the type.
- **Handlers are trusted code.** See step 11.
- **Secrets stay out of the folder you commit.** See step 12.

The same dashboard runs in a browser, served by the engine. You need Node.js 24 or newer and no desktop app. It works on any operating system.

```sh

```

With no arguments this is the `web` command. It prints a one-time login code and opens `http://127.0.0.1:8555/login` (a free port is used when 8555 is taken):

  Dashboard:   http://127.0.0.1:8555/login

| Option | Meaning |
|---|---|

| `--admin-port <n>` | The dashboard's port on `127.0.0.1`. Default 8555. |
| `--no-open` | Do not open the browser. |

### Several backends in one server

Every folder of the backends directory with a `backend.json` is a backend. Each one runs on its own public port, as in the desktop app, with its own database, media and logs. In the dashboard you can create a backend (you give it a name, and its folder is created in the backends directory), open a folder that you removed from the list, start and stop backends, and remove one from the list. Removing never deletes the folder. A new backend gets the first free port from 8443 up; change it in Settings.

### What is different from the desktop app

These actions change files or trust stores outside the backends directory, so the browser does not offer them. The page says so where it hides them.

- **Open folder / Show database file.** Use Export backup to get the files.
- **Trust on this Mac, an iOS simulator or an Android emulator.** Run `tempo-local-backend trust mac` (or `trust ios`, `trust android`) in a terminal on the machine that runs the server. Creating the certificate is available in the browser; it never changes a trust store.
- **Choose any folder.** Backends live in the backends directory.
- **Drop files on the window.** Use Upload files.

### Security

- **Local only.** The dashboard listens on `127.0.0.1`. A request with another `Host` name is refused, so a web page that rebinds its DNS name to your machine gets nothing. Backends' public APIs still listen on all interfaces so a phone can reach them.
- **The login code is not a token.** It is random, works once, expires after 10 minutes, and wrong tries are rate limited (5 per minute). It is never put in a URL. The page sends it in the body of `POST /__session`.
- **The session is a cookie.** It is `HttpOnly` (scripts cannot read it) and `SameSite=Strict`. On `http://127.0.0.1` the browser accepts it without `Secure`, so this setup is for your own machine only; a server behind HTTPS sets `Secure`. A session ends after 12 hours without a request, when you press Sign out, or when the server restarts.
- **CSRF.** Every change must send the CSRF token (a header, kept in the page's memory) and an `Origin` of the same host. Without both the server answers 403.
- **The admin token stays on the server.** The desktop app's per-launch token is never sent to a browser.
- **A strict content security policy.** Scripts only from the server itself (no inline scripts, no `eval`), and the page can only call the server it came from. Inline styles are allowed, for styles only: the code editor writes its theme colours into style elements at run time and cannot put a nonce on them. Its two workers are files of the same server, never a CDN. "Try it" calls go through the server, which trusts only that backend's own certificate.
