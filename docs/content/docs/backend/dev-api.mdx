<Callout title="Development only" type="warn">
  The dev API is a development tool. Its mock login accepts a public test user and issues opaque tokens that are not real JWTs. Never expose it to an untrusted network and never use it in production.
</Callout>

## Packages

| Package | Role |
| --- | --- |
| `@rn-tempo/api-contract` | The definition format: `defineEndpoint`, `resource`, `defineConfig` and request validation. It has no server code. |
| `@rn-tempo/dev-api` | The server, the data generator and the `tempo-api` command. |

Both are ESM packages for Node 22 or newer. `zod` 4.6.7 is a peer dependency of `@rn-tempo/api-contract`, pinned to the same version as the template, so schemas from your app and from the contract are the same Zod instance.

## Commit scopes

The shared commitlint config accepts the scopes `api`, `portal`, `api-contract`, `dev-api`, `backend` and `docker`.

## Define endpoints

Write endpoints with `defineEndpoint` from `@rn-tempo/api-contract`. Every part is a Zod schema.

```ts
import { defineEndpoint, resource } from '@rn-tempo/api-contract';
import { z } from 'zod';

const Item = z.object({ id: z.number(), title: z.string(), price: z.number() });

export const getProduct = defineEndpoint({
  method: 'GET',
  path: '/products/:id',
  params: z.object({ id: z.coerce.number() }),
  response: Item,
  // Optional. Leave it out to get data generated from `response`.
  data: ({ params, db }) => db.collection('products').get<z.input<typeof Item>>(params.id),
  scenarios: { notFound: { status: 404 }, slow: { delayMs: 3000 } },
});
```

| Option | Meaning |
| --- | --- |
| `method`, `path` | `path` is Express style, with `:param` segments. |
| `params`, `query`, `body` | Schemas for each request part. The parsed values (coerced, defaulted) reach `data`. |
| `response` | The success body. The server checks every response against it. |
| `status` | Success status. Defaults to 200. |
| `auth: 'bearer'` | Requires a token from the mock login. |
| `data` | Fixed data. It must return `z.input<typeof response>` or a promise of it, so a wrong shape is a compile error. |
| `scenarios` | Named canned responses `{ status?, delayMs?, body? }`. |
| `id` | Overrides the stable id, which is `<method>.<path>`, for example `get.products.:id`. |
| `summary`, `tags` | Used by the generated docs. |

`data` receives `{ params, query, body, db, headers }`. Each part is typed from its schema. `db.collection(name)` returns the stored collection of a `resource`. Throw `ApiError(404, 'Not found')` to answer with an error status.

### Resources

`resource(name, itemSchema, options)` expands to five endpoints that read and write one collection.

| Endpoint | Route |
| --- | --- |
| list | `GET /<name>?limit=&skip=&q=` answers `{ <name>: Item[], total, skip, limit }` |
| get | `GET /<name>/:id` |
| create | `POST /<name>/add` (201) |
| update | `PATCH /<name>/:id` |
| delete | `DELETE /<name>/:id`, answers the removed item |

Options: `seed` (a count to generate, or the items), `searchBy` (fields that `q` searches), `idField` (default `id`), `createSchema`, `updateSchema` and `listKey` (the key that holds the items in the list response).

### Config

```ts
import { defineConfig } from '@rn-tempo/api-contract';

export default defineConfig({
  endpoints: [getProduct, resource('products', Item, { seed: 50, searchBy: ['title'] })],
  basePath: '', // the real backend mounts the same endpoints under '/api/v1'
  port: 8443,
  seed: 1,
});
```

### Request errors

A request that fails validation gets a 400 `application/problem+json` response in RFC 9457 shape. Every invalid field is listed, prefixed with the request part:

```json
{
  "type": "about:blank",
  "title": "Invalid request",
  "status": 400,
  "detail": "1 field failed validation.",
  "errors": [{ "path": "body.email", "message": "Invalid email address" }]
}
```

## Data

Without a `data` function, the server generates the response from the Zod `response` schema.

- **Deterministic.** The same `seed` (from `defineConfig`), endpoint id and params always return the same body, so screenshots and tests are stable. Change `seed` to get a different set.
- **Realistic.** Field names pick realistic values: `email`, `phone`, `firstName`, `lastName`, `username`, `image`, `thumbnail`, `avatar`, `title`, `description`, `price`, `rating`, `stock`, `category`, `createdAt` and `updatedAt`. Values always satisfy the schema, so a `price` of `z.number().max(10)` stays under 10.
- **Constraints.** Min and max, string formats (`email`, `url`, `uuid`, `datetime` and more), simple regexes, enums, literals, unions, optional, nullable, default, records, tuples, dates and recursive schemas are all supported. Recursive schemas stop at a depth cap.
- **Overrides.** `.meta({ example: 'Fixed title' })` sets one field. `.describe('... example: SAVE10')` works too.

### Fixed data

Fixed data wins over generation, in this order:

1. The endpoint's `data` function.
2. `fixtures/<endpointId>.json`, next to the config file. Write the `:` of the id as `_` on Windows, for example `get.products._id.json`.
3. Generation.

A resource's first items follow the same idea: `seed: 50` generates 50 items (numeric ids count from 1), and `seed: [...]` lists them.

## How a request is handled

The server (`createServer(config, { dataDir })`, built on Express 5) runs every request through the same steps:

1. **Validate** params, query and body. A failure is a 400 problem+json that names each field.
2. **Check auth.** An endpoint with `auth: 'bearer'` returns 401 without a valid token.
3. **Pick a scenario.** The `x-tempo-scenario` header wins over the scenario set with `tempo-api scenario set`.
4. **Compute data** (`data`, fixture file, then generation).
5. **Check the response** against the `response` schema. If it does not match, the server answers 500 problem+json that says which field is wrong. It never sends invalid data. A 500 here means your `data` function or fixture is wrong, not the app.

Unknown routes get a 404 problem+json. Every response carries an `x-tempo-dev-api` header, so a mock is easy to recognize.

### Scenarios

A scenario is `{ status?, delayMs?, body? }`. Declare your own in `scenarios`, or use the built-in names that every endpoint has:

| Name | Effect |
| --- | --- |
| `notFound`, `unauthorized`, `forbidden`, `rateLimited` | 404, 401, 403, 429 problem+json |
| `serverError`, `unavailable` | 500, 503 problem+json |
| `slow` | Waits 3 seconds, then answers normally |

```sh
curl -H 'x-tempo-scenario: notFound' http://localhost:8443/products/1
```

A name that does not exist on the endpoint is a 400 that lists the available ones. Scenarios set with the CLI live in memory, so restarting the server clears them.

### Stored data

`resource` data lives in memory and is saved to `<dataDir>/db.json` (default `.tempo-api/`, gitignored) with atomic writes: a temp file, then a rename. A collection is seeded the first time it is used, so a restart keeps your edits. The store's `reset()` drops every collection and seeds it again. A `db.json` that cannot be read is renamed to `db.json.corrupt-<time>` and the server starts clean.

### Mock auth

Set `auth: true` in `defineConfig` to get the C13 endpoints:

| Route | Does |
| --- | --- |
| `POST /auth/login` | Accepts `emilys` / `emilyspass`. Answers the user plus `accessToken` and `refreshToken`. |
| `POST /auth/refresh` | Trades a refresh token for a new pair. The old refresh token stops working. |
| `GET /auth/me` | The signed-in user. Needs a bearer token. |

<Callout title="This is not real authentication" type="warn">
  The credentials are public. Tokens are random opaque strings (`tempo_dev_access_...`) kept in `db.json`, not signed JWTs, so nothing can be verified or read from them. Use this only on your own machine. The real backend (tier 2) has real accounts.
</Callout>

### Logs

Logs are JSON lines written with `pino`. Each request logs its method, path, status and time. At `debug` level the headers and bodies are logged too. Values of `authorization`, `cookie`, `password`, `token`, `refreshToken`, `accessToken`, `otp`, `code`, `email` and `phone` are replaced with `[REDACTED]` at any depth, in headers, bodies and query strings.

### Internal routes

| Route | Does |
| --- | --- |
| `GET /__tempo/health` | `{ ok, service, pid, startedAt, scenarios }`. Used by the CLI to check the server is the dev API. |
| `GET /__tempo/endpoints` | A list of endpoints: id, method, path, auth, tags and scenario names. |
| `POST /__tempo/scenario`, `POST /__tempo/reset` | Used by the CLI. They need the control token (header `x-tempo-token`). |

The server listens over plain HTTP in this phase. The listener accepts TLS options, which a later phase uses for local HTTPS.

## The tempo-api command

`@rn-tempo/dev-api` installs the `tempo-api` binary. Run it with `yarn tempo-api` (a later phase adds the `yarn api` shortcut to the template).

| Command | Does |
| --- | --- |
| `up [--port 8443] [--host 0.0.0.0]` | Starts the server in the background and waits until it answers. Prints the local URL, the LAN URL and a QR code of the LAN URL for a phone. If it is already running, it says so and exits 0. |
| `down` | Stops the server. |
| `status` | Shows whether it runs, its pid and any active scenarios. |
| `logs [-f] [-n 50] [--raw]` | Prints the log. `-f` keeps following it. |
| `reset` | Re-seeds the stored data. When the server is not running it deletes `db.json`, so the next start seeds again. |
| `scenario set <endpointId> <name>` | Makes one endpoint answer with a scenario until cleared. |
| `scenario clear [endpointId]` | Clears one scenario, or all of them. |
| `start` | Runs in the foreground. Use it in Docker or when debugging. |

Every command takes `--config <file>` (default `api/tempo-api.config.ts`) and `--cwd <dir>`.

### Config file

The config is a TypeScript file that default-exports `defineConfig(...)`. It is loaded without a build step, and it follows your `tsconfig.json` `paths`, so it can import the app's own schemas:

```ts
// api/tempo-api.config.ts
import { defineConfig, resource } from '@rn-tempo/api-contract';

import { ItemSchema } from '@features/items/schemas'; // an alias from tsconfig

export default defineConfig({
  auth: true,
  endpoints: [resource('products', ItemSchema, { seed: 50, searchBy: ['title'] })],
});
```

Fixture files go in `api/fixtures/`, next to the config.

### Endpoint ids

Every endpoint has a stable id, `<method>.<path>` in lowercase, with `/` written as `.` and the `:param` kept: `get.products.:id`. A `resource` uses `list.<name>`, `get.<name>`, `create.<name>`, `update.<name>` and `delete.<name>`. Set `id` on `defineEndpoint` to choose your own. List them with `GET /__tempo/endpoints`.

### What `up` and `down` keep in `.tempo-api/`

| File | Content |
| --- | --- |
| `server.pid` | The pid, port and host of the background server. |
| `server.log` | JSON log lines, redacted. |
| `db.json` | Stored resource data and mock tokens. |
| `control-token` | A random secret, readable only by you. The CLI sends it so only the local CLI can switch scenarios. |

`down` is careful. It stops only the process in its own pid file, and only after the recorded port answers the health check with that same pid. A stale pid file (the process is gone) is removed. A pid file that points at some other process is removed too, and that process is left alone.

<Callout title="LAN access" type="warn">
  `up` listens on all network interfaces by default so a phone can open the QR code URL. Anyone on the same network can reach the server and use its public test login. Use `--host 127.0.0.1` on a network you do not trust.
</Callout>
