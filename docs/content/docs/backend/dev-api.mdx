<Callout title="Development only" type="warn">
  The dev API is a development tool. Its mock login accepts a public test user and issues opaque tokens that are not real JWTs. Never expose it to an untrusted network and never use it in production.
</Callout>

## Packages

| Package | Role |
| --- | --- |
| `@rn-tempo/api-contract` | The definition format: `defineEndpoint`, `resource`, `defineConfig` and request validation. It has no server code. |
| `@rn-tempo/dev-api` | The server, the data generator and the `tempo-api` command. |

Both are ESM packages for Node 22 or newer. `zod` 4.6.7 is a peer dependency of `@rn-tempo/api-contract`, pinned to the same version as the template, so schemas from your app and from the contract are the same Zod instance.

## Commit scopes

The shared commitlint config accepts the scopes `api`, `portal`, `api-contract`, `dev-api`, `backend`, `docker` and `desktop`.

## Define endpoints

Write endpoints with `defineEndpoint` from `@rn-tempo/api-contract`. Every part is a Zod schema.

```ts
import { defineEndpoint, resource } from '@rn-tempo/api-contract';
import { z } from 'zod';

const Item = z.object({ id: z.number(), title: z.string(), price: z.number() });

export const getProduct = defineEndpoint({
  method: 'GET',
  path: '/products/:id',
  params: z.object({ id: z.coerce.number() }),
  response: Item,
  // Optional. Leave it out to get data generated from `response`.
  data: ({ params, db }) => db.collection('products').get<z.input<typeof Item>>(params.id),
  scenarios: { notFound: { status: 404 }, slow: { delayMs: 3000 } },
});
```

| Option | Meaning |
| --- | --- |
| `method`, `path` | `path` is Express style, with `:param` segments. |
| `params`, `query`, `body` | Schemas for each request part. The parsed values (coerced, defaulted) reach `data`. |
| `response` | The success body. The server checks every response against it. |
| `status` | Success status. Defaults to 200. |
| `auth: 'bearer'` | Requires a token from the mock login. |
| `data` | Fixed data. It must return `z.input<typeof response>` or a promise of it, so a wrong shape is a compile error. |
| `scenarios` | Named canned responses `{ status?, delayMs?, body? }`. |
| `id` | Overrides the stable id, which is `<method>.<path>`, for example `get.products.:id`. |
| `summary`, `tags` | Used by the generated docs. |

`data` receives `{ params, query, body, db, headers }`. Each part is typed from its schema. `db.collection(name)` returns the stored collection of a `resource`. Throw `ApiError(404, 'Not found')` to answer with an error status.

### Resources

`resource(name, itemSchema, options)` expands to five endpoints that read and write one collection.

| Endpoint | Route |
| --- | --- |
| list | `GET /<name>?limit=&skip=&q=` answers `{ <name>: Item[], total, skip, limit }` |
| get | `GET /<name>/:id` |
| create | `POST /<name>/add` (201) |
| update | `PATCH /<name>/:id` |
| delete | `DELETE /<name>/:id`, answers the removed item |

Options: `seed` (a count to generate, or the items), `searchBy` (fields that `q` searches), `idField` (default `id`), `createSchema`, `updateSchema` and `listKey` (the key that holds the items in the list response).

### Config

```ts
import { defineConfig } from '@rn-tempo/api-contract';

export default defineConfig({
  endpoints: [getProduct, resource('products', Item, { seed: 50, searchBy: ['title'] })],
  basePath: '', // the real backend mounts the same endpoints under '/api/v1'
  port: 8443,
  seed: 1,
});
```

### Request errors

A request that fails validation gets a 400 `application/problem+json` response in RFC 9457 shape. Every invalid field is listed, prefixed with the request part:

```json
{
  "type": "about:blank",
  "title": "Invalid request",
  "status": 400,
  "detail": "1 field failed validation.",
  "errors": [{ "path": "body.email", "message": "Invalid email address" }]
}
```

## Data

Without a `data` function, the server generates the response from the Zod `response` schema.

- **Deterministic.** The same `seed` (from `defineConfig`), endpoint id and params always return the same body, so screenshots and tests are stable. Change `seed` to get a different set.
- **Realistic.** Field names pick realistic values: `email`, `phone`, `firstName`, `lastName`, `username`, `image`, `thumbnail`, `avatar`, `title`, `description`, `price`, `rating`, `stock`, `category`, `createdAt` and `updatedAt`. Values always satisfy the schema, so a `price` of `z.number().max(10)` stays under 10.
- **Constraints.** Min and max, string formats (`email`, `url`, `uuid`, `datetime` and more), simple regexes, enums, literals, unions, optional, nullable, default, records, tuples, dates and recursive schemas are all supported. Recursive schemas stop at a depth cap.
- **Overrides.** `.meta({ example: 'Fixed title' })` sets one field. `.describe('... example: SAVE10')` works too.

### Fixed data

Fixed data wins over generation, in this order:

1. The endpoint's `data` function.
2. `fixtures/<endpointId>.json`, next to the config file. Write the `:` of the id as `_` on Windows, for example `get.products._id.json`.
3. Generation.

A resource's first items follow the same idea: `seed: 50` generates 50 items (numeric ids count from 1), and `seed: [...]` lists them.

## How a request is handled

The server (`createServer(config, { dataDir })`, built on Express 5) runs every request through the same steps:

1. **Check auth.** An endpoint with `auth: 'bearer'` returns 401 without a valid token, before anything else is looked at.
2. **Validate** params, query and body. A failure is a 400 problem+json that names each field.
3. **Pick a scenario.** The `x-tempo-scenario` header wins over the scenario set with `tempo-api scenario set`.
4. **Compute data** (`data`, fixture file, then generation).
5. **Check the response** against the `response` schema. If it does not match, the server answers 500 problem+json that says which field is wrong. It never sends invalid data. A 500 here means your `data` function or fixture is wrong, not the app.

Unknown routes get a 404 problem+json. Every response carries an `x-tempo-dev-api` header, so a mock is easy to recognize.

### Scenarios

A scenario is `{ status?, delayMs?, body? }`. Declare your own in `scenarios`, or use the built-in names that every endpoint has:

| Name | Effect |
| --- | --- |
| `notFound`, `unauthorized`, `forbidden`, `rateLimited` | 404, 401, 403, 429 problem+json |
| `serverError`, `unavailable` | 500, 503 problem+json |
| `slow` | Waits 3 seconds, then answers normally |

```sh
curl -H 'x-tempo-scenario: notFound' http://localhost:8443/products/1
```

A name that does not exist on the endpoint is a 400 that lists the available ones. Scenarios set with the CLI live in memory, so restarting the server clears them.

### Stored data

`resource` data lives in memory and is saved to `<dataDir>/db.json` (default `.tempo-api/`, gitignored) with atomic writes: a temp file, then a rename. A collection is seeded the first time it is used, so a restart keeps your edits. The store's `reset()` drops every collection and seeds it again. A `db.json` that cannot be read is renamed to `db.json.corrupt-<time>` and the server starts clean.

### Mock auth

Set `auth: true` in `defineConfig` to get the C13 endpoints:

| Route | Does |
| --- | --- |
| `POST /auth/login` | Accepts `emilys` / `emilyspass`. Answers the user plus `accessToken` and `refreshToken`. |
| `POST /auth/refresh` | Trades a refresh token for a new pair. The old refresh token stops working. |
| `GET /auth/me` | The signed-in user. Needs a bearer token. |

<Callout title="This is not real authentication" type="warn">
  The credentials are public. Tokens are random opaque strings (`tempo_dev_access_...`) kept in `db.json`, not signed JWTs, so nothing can be verified or read from them. Use this only on your own machine. The real backend (tier 2) has real accounts.
</Callout>

### Logs

Logs are JSON lines written with `pino`. Each request logs its method, path, status and time. At `debug` level the headers and bodies are logged too. Values of `authorization`, `cookie`, `password`, `token`, `refreshToken`, `accessToken`, `otp`, `code`, `email` and `phone` are replaced with `[REDACTED]` at any depth, in headers, bodies and query strings.

### Internal routes

| Route | Does |
| --- | --- |
| `GET /__tempo/health` | `{ ok, service, pid, startedAt, scenarios }`. Used by the CLI to check the server is the dev API. |
| `GET /__tempo/endpoints` | A list of endpoints: id, method, path, auth, tags and scenario names. |
| `GET /__tempo/info` | No token (it holds nothing secret). `{ service, version, project, scheme, port, urls: { local, lan?, androidEmulator, iosSimulator }, cert: { present, notAfter?, coversLanIp? }, startedAt }`. The process that starts the server fills in the scheme, port, LAN address and certificate status. |
| `GET /__tempo/events` | A server-sent event stream of the request log. Needs the control token. See [Request stream](#request-stream). |
| `GET /__tempo/data` | The stored `resource()` records, read-only, as `{ collections: [{ name, total, items }] }` (at most 500 items each), redacted like the request log. Needs the control token. The [desktop app](/docs/backend/desktop-app)'s Data screen reads it. |
| `GET /__tempo/ca.pem` | The **public** root CA (`.tempo-api/certs/rootCA.pem`), as `application/x-pem-file`, so a phone can download it. 404 when `tempo-api certs` has not run. It reads that one file only, never a key, and refuses a file that holds a private key block. |
| `POST /__tempo/scenario`, `POST /__tempo/reset` | Used by the CLI. They need the control token (header `x-tempo-token`). |

### Request stream

`GET /__tempo/events` (header `x-tempo-token`) is a `text/event-stream`. The server keeps the last 500 requests in memory. A new client first gets those, then each new request as it finishes. Every message is `id: <n>`, `event: request` and `data: <json>`. A client that reconnects with `Last-Event-ID` only gets the entries after that id. A `: keep-alive` comment line is sent every 15 seconds, and closing the connection removes its listener and timer.

```json
{
  "id": 7, "at": "2026-11-17T08:30:00.000Z", "method": "POST", "url": "/auth/login",
  "status": 200, "ms": 4, "scenario": "slow",
  "req": { "headers": { "authorization": "[REDACTED]" }, "body": { "username": "emilys", "password": "[REDACTED]" } },
  "res": { "body": { "accessToken": "[REDACTED]" } }
}
```

Entries are built with the same redaction as the log (at every log level), including query strings. A body longer than 32 KB is cut to its first 32 KB of JSON text and the side gets `"truncated": true`. Requests to `/__tempo/*` are not listed.

The server listens over plain HTTP in this phase. The listener accepts TLS options, which a later phase uses for local HTTPS.

## The tempo-api command

`@rn-tempo/dev-api` installs the `tempo-api` binary. Run it with `yarn tempo-api` (a later phase adds the `yarn api` shortcut to the template).

| Command | Does |
| --- | --- |
| `up [--port 8443] [--host 0.0.0.0] [--http]` | Starts the server in the background and waits until it answers. Serves HTTPS when a certificate exists (see [Local HTTPS](/docs/backend/local-https)); `--http` forces plain HTTP. Prints the local URL, the LAN URL and a QR code of the LAN URL for a phone. If it is already running, it says so and exits 0. |
| `certs [--out dir] [--host name] [--install]` | Creates a local HTTPS certificate with mkcert. |
| `trust ios` / `trust android` | Trusts the local CA on a simulator or emulator. |
| `dev ios` / `dev android [--port] [--http]` | The daily command: creates certificates when missing, then `trust ios` (booted simulator) or `trust android --push` (prints the install steps), then `up`. With `--http` it skips certificates and trust and only starts the server. |
| `down` | Stops the server. |
| `status` | Shows whether it runs, its pid and any active scenarios. |
| `logs [-f] [-n 50] [--raw]` | Prints the log. `-f` keeps following it. |
| `reset` | Re-seeds the stored data. When the server is not running it deletes `db.json`, so the next start seeds again. |
| `scenario set <endpointId> <name>` | Makes one endpoint answer with a scenario until cleared. |
| `scenario clear [endpointId]` | Clears one scenario, or all of them. |
| `start` | Runs in the foreground. Use it in Docker or when debugging. |
| `openapi`, `collections`, `msw`, `generate` | Write the generated files. See [Generators](#generators). |
| `check` | Fails when a generated file is out of date. |
| `import openapi <file> [--out tempo-api.json] [--force]` | Turns an OpenAPI 3.0/3.1 file (JSON or YAML) into a [JSON workspace](#json-workspaces). |
| `export code [--config tempo-api.json] [--out <project>] [--force]` | Writes a TypeScript config and endpoint files from a JSON workspace. |

Every command takes `--config <file>` (default `api/tempo-api.config.ts`) and `--cwd <dir>`.

### Standalone build

`yarn workspace @rn-tempo/dev-api build` also writes `dist/standalone/tempo-api.mjs` (about 4 MB) with every dependency inlined, plus a `swagger-ui/` folder (about 2 MB) that it finds next to itself. It runs with no `node_modules`:

```sh
node tempo-api.mjs up --cwd /path/to/project
```

The project's own config still imports `@rn-tempo/api-contract` and `zod` from the project's `node_modules`. The desktop app bundles this build for projects that have no `@rn-tempo/dev-api`. It is not part of the npm package (`files` lists only the small build), because it is about 50 times larger.

### Config file

The config is a TypeScript file that default-exports `defineConfig(...)`. It is loaded without a build step, and it follows your `tsconfig.json` `paths`, so it can import the app's own schemas:

```ts
// api/tempo-api.config.ts
import { defineConfig, resource } from '@rn-tempo/api-contract';

import { ItemSchema } from '@features/items/schemas'; // an alias from tsconfig

export default defineConfig({
  auth: true,
  endpoints: [resource('products', ItemSchema, { seed: 50, searchBy: ['title'] })],
});
```

Fixture files go in `api/fixtures/`, next to the config.

### Endpoint ids

Every endpoint has a stable id, `<method>.<path>` in lowercase, with `/` written as `.` and the `:param` kept: `get.products.:id`. A `resource` uses `list.<name>`, `get.<name>`, `create.<name>`, `update.<name>` and `delete.<name>`. Set `id` on `defineEndpoint` to choose your own. List them with `GET /__tempo/endpoints`.

### What `up` and `down` keep in `.tempo-api/`

| File | Content |
| --- | --- |
| `server.pid` | The pid, port and host of the background server. |
| `server.log` | JSON log lines, redacted. |
| `db.json` | Stored resource data and mock tokens. |
| `control-token` | A random secret, readable only by you. The CLI sends it so only the local CLI can switch scenarios. |

`down` is careful. It stops only the process in its own pid file, and only after the recorded port answers the health check with that same pid. A stale pid file (the process is gone) is removed. A pid file that points at some other process is removed too, and that process is left alone.

<Callout title="LAN access" type="warn">
  `up` listens on all network interfaces by default so a phone can open the QR code URL. Anyone on the same network can reach the server and use its public test login. Use `--host 127.0.0.1` on a network you do not trust.
</Callout>

## JSON workspaces

A project does not have to write TypeScript. A **workspace** is one JSON file, `tempo-api.json`, that describes the endpoints as data. The server reads it like a code config, so everything else (scenarios, Swagger, Postman, `check`) works the same.

```json
{
  "name": "shop",
  "basePath": "/api/v1",
  "port": 8443,
  "seed": 7,
  "endpoints": [
    {
      "id": "get.products.:id",
      "method": "GET",
      "path": "/products/:id",
      "summary": "One product",
      "tags": ["products"],
      "auth": "bearer",
      "request": {
        "params": { "type": "object", "properties": { "id": { "type": "integer" } }, "required": ["id"] },
        "query": { "type": "object", "properties": { "lang": { "type": "string" } } }
      },
      "response": {
        "status": 200,
        "schema": { "type": "object", "properties": { "id": { "type": "integer" }, "title": { "type": "string" } }, "required": ["id", "title"] },
        "example": { "id": 1, "title": "Fixed" }
      },
      "scenarios": { "gone": { "status": 410, "body": { "message": "gone" } }, "slow": { "delayMs": 2000 } }
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `name`, `basePath?`, `port?`, `seed?` | Like the code config. |
| `endpoints[].id`, `method`, `path` | `path` uses `:param` segments. `id` is what scenarios use. |
| `summary?`, `tags?`, `auth?: "bearer"` | As in `defineEndpoint`. A bearer endpoint turns on the mock login (`/auth/login`), so a client can get a token. |
| `request.params`, `request.query`, `request.body` | Each a JSON Schema. Path and query values arrive as text, so `integer` and `number` are coerced and `boolean` reads `true` or `false`. |
| `response.status`, `schema?`, `example?` | `example` is served as given. Without it, data is generated from `schema` with the seed. An example that fails its own schema is dropped with a warning, because the server would otherwise answer 500. With neither, the body is `{}` (nothing for a 204). |
| `scenarios?` | The same shape as in code: `status`, `delayMs`, `body`. |

The file is checked with a Zod schema, and every problem is reported with its path. The JSON Schema of the file is `schemas/tempo-api.schema.json` in the package. Point an editor at it for completion, for example with `"$schema": "./node_modules/@rn-tempo/dev-api/schemas/tempo-api.schema.json"`. It is generated from the Zod schema (`yarn workspace @rn-tempo/dev-api schema`), and a test fails when the two differ.

**How it is loaded.** Pass `--config tempo-api.json` (any path that ends in `.json`), or leave `--config` out: when `api/tempo-api.config.ts` does not exist and `tempo-api.json` is in the project folder, that file is used. JSON Schema becomes Zod with Zod 4's own `z.fromJSONSchema`, so the schemas are the ones Zod reads (draft 2020-12, local `$defs`/`$ref`). The OpenAPI 3.0 dialect (`nullable`) is turned into JSON Schema by the importer.

### Import an OpenAPI file

```sh
tempo-api import openapi ./petstore.yaml --out tempo-api.json
tempo-api up --config tempo-api.json
```

It reads OpenAPI 3.0 and 3.1, as JSON or YAML (the `yaml` package). Swagger 2.0 is not supported. Per operation it takes:

- the path (`{id}` becomes `:id`), method, summary and tags,
- path-level and operation-level parameters (`path` and `query`; header and cookie parameters are skipped),
- the JSON request body schema,
- the first 2xx response with its JSON schema and example (`example`, the first of `examples`, or the schema's own),
- `security` (operation or document level) as `auth: "bearer"`,
- the first server URL's path as `basePath`.

Local `$ref`s are inlined. A schema that contains itself is cut to "any" where it repeats, and non-local references become "any"; both give a warning. `head`, `options` and `trace` are skipped with a warning. Error responses (4xx and 5xx) are not imported; add them as scenarios. The command refuses to overwrite its output without `--force`. Importing the template's own `api/generated/openapi.json` gives a workspace that serves all 13 endpoints.

### Export to code

```sh
tempo-api export code --out ./my-project
```

From a workspace, it writes `api/tempo-api.config.ts` and one `api/endpoints/<tag>.ts` per first tag (`default.ts` for untagged endpoints), each endpoint as `defineEndpoint` with Zod schemas. It refuses to touch any existing file unless you pass `--force`, and checks all targets before writing the first.

The JSON Schema to Zod step handles this subset: `type` (string, number, integer, boolean, null, array, object, or a list), `enum`, `const`, `anyOf`/`oneOf` (a `null` branch gives `.nullable()`), `allOf`, string `format` (`email`, `uuid`, `date-time`, `date`, `uri`), `minLength`, `maxLength`, `pattern`, the number bounds, `minItems`, `maxItems`, `items`, `properties`, `required` and `additionalProperties`. Anything else becomes `z.unknown()`. Run Prettier on the result. After export, delete or ignore `tempo-api.json`, because the code config wins when both exist.

## The runtime entry

The request steps above live in one function, `createRuntime(config, options)`, exported from `@rn-tempo/dev-api/runtime`. The Express server, the MSW handlers for Jest and the in-app mock adapter all call it, so the three cannot drift apart.

```ts
import { createRuntime } from '@rn-tempo/dev-api/runtime';

const runtime = createRuntime(config);
const { status, body } = await runtime.resolve({
  method: 'GET',
  path: '/products',
  query: { limit: '2' },
  headers: { authorization: 'Bearer ...' },
});
```

| Member | Does |
| --- | --- |
| `resolve(request)` | Runs auth, validation, scenario, data and the response check. It never throws: every failure is a problem+json response. |
| `matches(method, path)` | Tells whether an endpoint answers. The in-app adapter uses it to let other requests reach the network. |
| `endpoints` | The endpoints in match order (static segments before `:param` ones). |
| `store` | The in-memory store behind `db.collection(...)` and the mock tokens. |

The entry imports only `@rn-tempo/api-contract` and `zod`. It has no Express, no `pino` and no `node:` module, and a test checks that. The server adds what needs Node: it saves the store to `db.json` and passes `fallbackData`, which reads fixture files and generates data.

<Callout title="No faker in the app" type="warn">
  Generating data needs `@faker-js/faker`, which belongs in Node only. In Jest and in the app, every endpoint must have a `data` function (the C13 endpoints do), because the runtime has no generator there. An endpoint without `data` answers a 500 that says so. A resource whose `seed` is a count needs the server; list its items to use it without one.
</Callout>

## Generators

All outputs come from the endpoint definitions, so nothing is written by hand twice. Files go to `generated/` next to the config (`api/generated/`).

| Command | File | Contents |
| --- | --- | --- |
| `tempo-api openapi` | `openapi.json` | OpenAPI 3.1. |
| `tempo-api collections` | `postman.collection.json`, `postman.environment.json` | A Postman collection (v2.1) and an environment. |
| `tempo-api msw` | `msw-handlers.ts` | The MSW handlers for Jest. |
| `tempo-api generate` | all four | |
| `tempo-api check` | none | Regenerates into a temporary folder and exits 1 when any file differs or is missing. |

### OpenAPI

Schemas come from `z.toJSONSchema`. OpenAPI 3.1 uses JSON Schema 2020-12, which is Zod's default target, so no conversion is needed. Request parts use `io: 'input'` (what a client sends, before coercion and defaults) and responses use `io: 'output'`. Anything JSON Schema cannot hold, such as `z.date()` or a transform, becomes an open schema instead of failing the whole document.

- Paths come from the method, the path (`:id` becomes `{id}`) and the `params` and `query` schemas.
- Each body and response is a component, `PostAuthLoginRequest` and `PostAuthLoginResponse` for example. Errors share one `Problem` component.
- Scenarios with a status become documented responses, and `auth: 'bearer'` adds a security requirement and a 401.
- Request bodies and success responses carry an example, generated from the schema with the config `seed`.
- Keys are sorted and nothing random is written, so a diff shows only real changes.

### Swagger UI

`tempo-api up` serves Swagger UI at `/docs`, reading `/docs/openapi.json`. The document is built from the running config. The UI files come from the pinned `swagger-ui-dist` package. Only its scripts, styles and icons are served.

### Postman

The collection is built straight from the OpenAPI document by a small generator in `@rn-tempo/dev-api`, not with `openapi-to-postmanv2`. That converter puts random ids in its output, so `api:check` could never pass, and it brings a large dependency tree for a mapping this small. Our output is deterministic.

- Folders are the tags. Each request has `{{baseUrl}}`, the example body and, for protected endpoints, bearer auth with `{{token}}`.
- A request whose response holds an `accessToken` (the login) stores it in the `token` variable, so the others work right after.
- The environment holds `baseUrl` (`http://localhost:<port>`) and an empty `token`. It has no secrets.

### MSW handlers

`api/generated/msw-handlers.ts` is a few lines. It imports the config and calls `toMswHandlers(config, { http, HttpResponse })`. Handlers are not written out one by one, so there is nothing to drift. The file is generated, instead of asked for, so its import path to the config is right and `api:check` notices a hand edit.

`toMswHandlers` takes `http` and `HttpResponse` from your own `msw` install. That way there is one copy of `msw` (a second copy would give mismatched types) and `@rn-tempo/dev-api` does not import it. Handler paths start with `*`, so any host matches and an API base URL override keeps working. Use `server.use(...)` in a test to override one endpoint.

## In the template

Every generated app ships with `api/`, the one place where the C13 endpoints are defined:

```text
api/
  tempo-api.config.ts   lists the endpoints
  endpoints/            auth, authExtra, users, products, appConfig
  generated/            openapi.json, postman.*.json, msw-handlers.ts (never edit)
  README.md
```

| Script | Does |
| --- | --- |
| `yarn api <command>` | Runs `tempo-api`: `up`, `down`, `status`, `logs`, `reset`, `scenario`, `generate`, `check`. |
| `yarn api:check` | Fails when `api/generated` is out of date. It is part of `yarn verify` and of the pre-commit hook. |
| `yarn tempo g endpoint <feature>.<name>` | Adds an endpoint: its definition, registration, schemas, request function, query key and hook. See [Add an endpoint](/docs/guides/add-an-endpoint). |

`@rn-tempo/api-contract` and `@rn-tempo/dev-api` are `devDependencies`. The scripts run the binary from `node_modules`, which works for a published package and for the `link:` dependency used inside the rn-tempo repository (run `yarn build:tools` once at the repository root there; it builds `tempo-api` and `tempo`). `.tempo-api/` (pid, log, stored data, control token) is gitignored.

### The C13 endpoints are fixed on purpose

The endpoints that the app and its tests rely on have a `data` function with exact values: `Product N` with price `5 + N`, one demo user, the tokens `mock-access-token` and `mock-refresh-token`, the code `123456` for OTP. They never use generated data. That keeps the behavior identical in all three places and keeps faker out of the app bundle. A new endpoint can use generated data on the dev server, but anything that runs in Jest or in the app needs a `data` function.

### Plain schema imports

The config is loaded by Node (`jiti`, with the `tsconfig` paths), not React Native. Definitions must import schemas from plain modules:

| Use | Do not use |
| --- | --- |
| `@features/items/api/schemas` | `@features/items` (the barrel exports screens) |
| `@features/auth/api/schemas`, `@features/auth/types` | `@features/auth` |
| `@shared/utils/schemas` | `@shared/utils` (exports haptics and platform helpers) |

ESLint has an `api` element in the boundaries config: files under `api/` may import only these plain modules, `@shared`, `@services` and `@config`, and `msw` only in `api/generated`. `yarn api:check` fails if an import still reaches React Native.

### Optional modules

Endpoints of the items sample belong to the `samples` module. They sit inside `// @tempo-feature:samples:start` and `:end` markers in `api/tempo-api.config.ts`, and `api/endpoints/products.ts` is in the manifest's `deleteGlobs`. After removing the module, run `yarn api generate` to refresh `api/generated`.

### Jest and the in-app mock mode

The hand-written mock routes are gone. Both consumers answer from `api/`:

| Consumer | Where | How |
| --- | --- | --- |
| Jest | `src/test-utils/msw/handlers` | Re-exports `handlers` from `api/generated/msw-handlers.ts`. Override one answer with `server.use(...)` as before. |
| Dev mock mode (`API_MOCKING=true`) | `src/services/http/devMockAdapter.ts` | An axios adapter that asks the runtime whether an endpoint matches. A match is answered after the artificial latency, and every other request reaches the network. |

`src/test-utils/msw/routes` keeps what is not an endpoint: the path matcher (`matchPath` is the runtime's), the `MockRoute` shape for adapter tests that pass their own table, and `routes`, the endpoints as plain routes derived from `api/`. The constants tests use (`MOCK_ACCESS_TOKEN`, `mockUser`, `mockAppConfig`) are re-exported from `api/endpoints`.

The `@api/*` alias points to the root `api/` folder. It is the one alias outside `src/`, used by `src/test-utils` and the mock adapter.

The adapter and the runtime are loaded through a guarded `require` that Metro removes from release bundles. A release bundle contains no `faker`, `express`, `@rn-tempo/dev-api`, `createRuntime` or fixed mock token, and it has the same size as before the migration (checked with `react-native bundle --dev false`). Inside the rn-tempo repository, `metro.config.js` also watches the linked packages, so the dev bundle can resolve them.
