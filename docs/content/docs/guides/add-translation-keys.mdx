---
title: Add translation keys
description: Add strings to a namespace in English and Arabic, use typed keys, plurals, context and in-sentence formatting, and run the i18n check.
---

Every user-facing string is a key in both `en` and `ar`. Literal text in JSX is a lint error (`i18next/no-literal-string`).

## Steps

1. **Pick the namespace.** Files are `src/locales/<lang>/<namespace>.json`. The built-in namespaces are `common`, `errors`, `validation`, `auth`, `home`, `profile`, `settings`, `items`, `app` and `forms`. A new feature adds its own namespace file in both languages and registers it in `src/services/i18n/resources.ts`.

2. **Add the key to both files**, nested camelCase:

   ```json
   { "login": { "submitButton": "Sign in" } }
   ```

   Put the Arabic text under the same key in `src/locales/ar/auth.json`. The key sets of `en` and `ar` must be identical, except that plural forms differ per language (see below).

3. **Use it** with a string key. Keys are typed from the English JSON, so a typo or a renamed key is a type error:

   ```tsx
   const { t } = useTranslation('auth');
   <Text>{t('login.submitButton')}</Text>;
   ```

   From another namespace, pass `ns`: `t('actions.close', { ns: 'common' })`. The shared `Text` takes a key in `tx`, for example `tx="sheet.close"` (the `common` namespace). The selector form `t(($) => $.a.b)` is a lint error, so the codebase keeps one style.

4. **Plurals.** Pass `count` and add one key per plural form with the i18next suffixes. English needs `_one` and `_other`. Arabic needs all six: `_zero`, `_one`, `_two`, `_few`, `_many` and `_other`. The check below fails when an Arabic form is missing.

   ```json
   {
     "list": {
       "count_one": "{{count, number}} item",
       "count_other": "{{count, number}} items"
     }
   }
   ```

   ```tsx
   t('list.count', { count });
   ```

   Use the base key (`list.count`), never a suffixed one. Arabic counts of 0, 1, 2, 3, 11 and 100 select `zero`, `one`, `two`, `few`, `many` and `other`.

5. **Context (gender and role variants).** Name the variants `<key>_male` and `<key>_female` (or `_admin` and `_user`) and pass the value as `context`:

   ```json
   { "greeting": "مرحبًا، {{name}}", "greeting_male": "مرحبًا بك، {{name}}", "greeting_female": "مرحبًا بكِ، {{name}}" }
   ```

   ```tsx
   t('greeting', { name, context: gender });
   ```

   Any other context value falls back to the base key. The Home greeting is the working example. The config option `extract.preserveContextVariants` keeps the variants, because the context is computed at runtime.

6. **Numbers, money and dates inside a sentence** use the formatters built into i18next, so they follow the active language. Pass the raw value:

   ```json
   {
     "stock": "In stock: {{stock, number}}",
     "price": "Total {{amount, currency(USD)}}",
     "slots": "Slots for {{date, datetime(dateStyle: medium)}}"
   }
   ```

   ```tsx
   t('stock', { stock: 12345 });
   t('slots', { date: new Date() });
   ```

   Values that are not part of a sentence (a price on its own line, a table cell) keep using `formatCurrency`, `formatNumber` and `formatDate` from `@shared/utils`. Register an app-specific formatter with `i18n.services.formatter.add` in `services/i18n` only when no built-in does the job.

7. **Keys stored as data.** Zod messages, error maps and slide lists hold keys in a variable, where the extractor cannot see a `t()` call. Declare each one with a comment hint next to it; `extract --ci` reads comment hints, so the key is not removed as unused:

   ```ts
   // t('name.tooShort', { ns: 'validation' })
   z.string().min(2, 'name.tooShort');
   ```

   Never build a key with a template literal (``t(`status.${s}`)``): it is a lint error. Map values to keys with an `as const` object typed with `ParseKeys<'ns'>` instead.

8. **Run `yarn i18n:check`.** It runs `i18next-cli lint` (concatenation, punctuation and placeholder checks, all errors) and `i18next-cli extract --ci`. The extract step fails when the locale files are out of step with the code: a key removed from code but still in the JSON, a missing Arabic plural form, a missing translation, or conflicting defaults.

9. **Check it on screen in Arabic.** Switching language restarts the app to apply RTL. Look for clipped text and mirrored layouts; see the [device test matrix](/docs/guides/device-test-matrix).

## Missing keys in development

In a development build, a key that no language has logs a warning with the language, namespace and key (never the values). Release builds are unchanged. i18next `debug` turns on only when `LOG_LEVEL=debug`.

## Rules

- Validation messages from Zod are keys in the `validation` namespace.
- Dates, numbers and currency outside a sentence go through the `Intl` helpers in `@shared/utils`, not string building.
- Never call `I18nManager` directly; use `changeLanguage` from the language manager.
