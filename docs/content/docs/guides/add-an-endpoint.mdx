---
title: Add an endpoint
description: Generate the schema, request function and hook for an API endpoint, and a matching endpoint in backend/backend.json.
---

An endpoint has two sides: the app code (a Zod schema, a request function, a query key and a hook) and the endpoint in your backend that answers it. `tempo g endpoint` writes both. The backend side is an entry in `backend/backend.json`, which the [Tempo Local Backend](/docs/backend/local-backend) serves.

```sh
yarn tempo g endpoint items.getItem --path /items/:id
yarn verify
```

## What the generator writes

For `items.getItem` (feature `items`, name `getItem`), with `--method GET` as the default:

| File | Change |
| --- | --- |
| `src/features/items/api/schemas.ts` | `GetItemResponseSchema` and its type: a stub with `id`. A body method also gets `<Name>RequestSchema`. |
| `src/features/items/api/items.api.ts` | `getItem(id)`: `request(...)` with the response schema. |
| `src/features/items/api/keys.ts` | A `getItem(id)` key under the feature's key factory. |
| `src/features/items/api/queries.ts` | `useGetItemQuery(id)`, for a `GET`. Other methods get `useXMutation()` in `mutations.ts`, which invalidates the feature's keys. |
| `backend/backend.json` | A `static` endpoint with the method, the path, status 200, the body `{ "id": 1 }` and no response wrapper. |

The feature must exist (`tempo g feature items`). Existing files are extended, never overwritten. A name that already exists is an error, and so is an endpoint in `backend/backend.json` with the same method and path (or the same id). `--dry-run` shows what would change. When the project has Prettier installed, the generated app code is formatted with it. `backend/backend.json` is written as JSON with two-space indentation and keeps its existing key order.

When the project has no `backend/backend.json`, the app code is still generated and the result says that no backend was found: add the endpoint to your backend yourself.

| Option | Meaning |
| --- | --- |
| `--method` | `GET` (default), `POST`, `PUT`, `PATCH` or `DELETE`. |
| `--path` | The route, with `:params`. The default is `/<feature>/<name-in-kebab-case>`. |
| `--resource` | List, get, create, update and delete of one record type. It writes five request functions, list and detail keys and five hooks. In `backend/backend.json` it adds a collection (named like the record type, with a `title` field and three rows) and five `crud` endpoints, with `POST /<path>/add` as an alias of create. The name is the record type, for example `items.products`, and the default path is `/products`. |

## The steps after generating

1. **Replace the stubs.** The response schema holds only `id`. Describe the real fields in `schemas.ts`. The app parses responses with that schema, so a wrong answer from the backend fails loudly.
2. **Replace the example body.** Edit the endpoint in the Tempo Local Backend app, or in `backend/backend.json`, so it answers what the schema describes. For `--resource`, replace the stub `title` field and the seed rows of the collection.
3. **Run `yarn verify`.**

## Rules to remember

- **Optional modules.** Endpoints of an optional module stay in `backend/backend.json` when the module is removed with `tempo feature remove`: delete the ones the app no longer calls.
- **Scenarios** (`scenarios: { name: { status, body, delayMs } }`) are selected with the `x-tempo-scenario` header or in the Tempo Local Backend app.
